# AI 项目开发指南

> 基于 ricse（区域产业链服务生态平台）从 0 到 1 的实际协作经验提炼。
> 适用场景：AI（Claude Code）辅助下的全栈项目开发。

---

## 一、核心理念

### 1.1 人机协作模式

```
用户（需求方 + 验收方）←→ AI（执行方 + 建议方）
         ↑                      ↑
    决策、方向、标准      代码、方案、调研
    验收、纠偏            文档、解释
```

- **用户定方向**：描述需求、确认方案、验收结果
- **AI 落地执行**：写代码、查资料、提方案
- **用户纠偏**：不满意直接说，AI 调整
- **AI 主动建议**：发现更好的方案时主动提出

### 1.2 迭代节奏

1. **用户提出需求** → 一句话描述想要什么
2. **AI 理解 + 确认** → 复述理解，必要时提问澄清
3. **AI 执行** → 写代码、改文件、跑验证
4. **用户验收** → 看效果，反馈问题
5. **AI 修复** → 根据反馈调整，直到用户满意
6. **循环** → 进入下一个需求

### 1.3 关键原则

| 原则 | 说明 |
|------|------|
| **不让 AI 猜测** | 有原型就给原型，有规范就给规范 |
| **不给 AI 设限** | 相信 AI 的编码能力，说"要什么"而非"怎么做" |
| **不满意就直说** | 不绕弯子，"这个不对""需要改"最有效 |
| **逐步收窄** | 先确定大方向，再打磨细节 |
| **知识沉淀** | 每次对话的关键决策记入记忆系统，避免重复沟通 |

## 二、项目启动流程

### 2.1 从 0 到 1 的标准步骤

```
Step 1: 项目初始化
  ├── 技术栈选型（前端/后端/数据库/部署）
  ├── 创建 monorepo 结构
  ├── 配置开发环境（docker-compose、CI）
  └── 建立基础脚手架

Step 2: 文档体系搭建
  ├── CLAUDE.md（AI 协作约定）
  ├── Sot.md（Source of Truth，关键决策记录）
  ├── 项目启动文档（背景、范围、架构）
  └── 更新记录（变更追溯）

Step 3: UI 体系建立
  ├── 组件库配置（shadcn/ui）
  ├── 设计系统（色彩 token、组件规范）
  └── 布局框架（侧边栏、顶栏、内容区）

Step 4: 模块迭代
  ├── 模块设计文档 → 后端 API → 前端页面
  └── 使用指南（面向运营人员）

Step 5: 持续打磨
  ├── UX 审计（对比原型修正差异）
  ├── 代码审查
  └── 文档更新
```

### 2.2 文件结构标准

```
项目根/
├── docs/
│   ├── Sot.md              ← 所有关键决策的唯一真相入口
│   ├── 更新记录.md          ← 文档变更追溯
│   ├── 产品/                ← 面向业务方
│   │   ├── 功能特性.md       ← PRD/功能需求
│   │   ├── 01_角色文档.md    ← 按角色划分
│   │   └── 使用指南/         ← 操作手册
│   └── 技术/                ← 面向开发团队
│       ├── 技术架构.md
│       ├── 开发规则.md
│       ├── 设计系统.md
│       ├── 迭代计划.md
│       ├── 模块设计/
│       ├── adr/             ← 架构决策记录
│       └── prompt记录/      ← 有效 prompt 归档
├── CLAUDE.md                ← AI 协作约定（项目背景、技术栈、加载顺序）
└── apps/                    ← 应用代码
```

## 三、沟通规范

### 3.1 需求描述最佳实践

**✅ 好的描述：**
> "左侧菜单，未打开时候需要折叠起来，一级标题不应该小于下一级的。参照一下ux-prototype,icon也需要"

- 明确要什么（折叠、对齐）
- 给出参考（ux-prototype）
- 补充细节（icon也需要）

**✅ 纠偏反馈：**
> "现在有bug，点击二级菜单会出现自动折叠的情况。此外，点击选中和hover的状态，背景色应该占满整行。"

- 指出具体问题
- 描述期望状态
- 提供空间条件（"占满整行"）

### 3.2 常见指令速查

| 场景 | 推荐说法 |
|------|---------|
| 提需求 | "需要XX功能" / "参照原型做XX" |
| 不满意 | "这个不对" / "XX需要改" / "还不够" |
| 修问题 | "XX有bug" + 描述现象 |
| 确认 | "好的" / "第一个" / "继续" |
| 对比 | "跟原型/设计稿对比一下还有什么问题" |
| 查询 | "检查一下XX" / "XX在哪个位置" |

### 3.3 AI 应自动完成的检查

- TypeScript 类型检查（`npx tsc --noEmit`）
- 设计系统颜色 token 一致性
- 硬编码颜色扫描
- 原型对比检查

## 四、技术执行规范

### 4.1 前端规范

**组件选用优先级：**
1. shadcn/ui 内置组件（Button、Card、Badge、Input 等）
2. 自定义组件（用 shadcn 风格 + Radix UI 原语）
3. 避免 Ant Design 等第三方 UI 库混用

**颜色系统（基于本项目经验）：**

```css
/* globals.css 中定义 HSL 变量 */
--primary: 221.2 83.2% 53.3%;
--success: 142 76% 36%;
--warning: 41 96% 40%;
--info: 192 91% 36%;
--primary-bg: 214 100% 97%;
--success-bg: 138 76% 97%;
```

```tsx
// tailwind 中使用语义别名
bg-primary-bg    /* 主色背景 */
text-success     /* 成功文字 */
bg-warning-bg    /* 警告背景 */
text-destructive /* 危险文字 */
// 不要用：
bg-blue-600      /* ✗ 硬编码 */
text-gray-500    /* ✗ 硬编码 */
```

**侧边栏（本项目核心模式）：**
- 暗色背景 + 手风琴菜单
- Collapsed 64px / Expanded 256px
- 一级标题 `text-[#cbd5e1]`，二级 `text-sidebar-foreground/65`
- 激活态：蓝色左边框 3px + 背景高亮 + `#93c5fd` 文字
- `<button>` 必须加 `type="button"`（防止浏览器自动提交行为导致滚动到顶部）
- 子项 `pl-[38px]` 对齐标题文字位置

### 4.2 后端规范

- NestJS + TypeScript + Prisma ORM
- PostgreSQL 数据库
- 模块化单体（非微服务）
- DDD 分层：domain / application / infrastructure / interfaces
- REST API + OpenAPI 文档（@nestjs/swagger）

### 4.3 常见陷阱避坑（本项目实际踩过的）

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 前端空白页 | 安装`tw-animate-css`（Tailwind v4包）不兼容Tailwind v3 | 移除+清空`.next`缓存 |
| `bg-primary-600`不存在 | Tailwind只有custom `primary`（DEFAULT），无600/700 | 用`bg-primary text-primary-foreground` |
| 侧边栏滚动到顶部 | `<button>`默认type=submit | 加`type="button"` |
| 导航高亮混乱 | query params匹配策略不对 | 用useSearchParams做精确匹配 |
| 手风琴不能关闭 | active子项强制保持展开 | 用`useState` + `useEffect`组合而非`isActuallyExpanded` |

## 五、UX 原型驱动开发

### 5.1 流程

```
静态原型（HTML） → AI 阅读分析 → 按原型实现 → 对比审计 → 修复差异
```

### 5.2 审计方法

AI 可以做系统性对比检查：

1. 列出原型所有页面/组件
2. 逐项对比当前实现
3. 按严重程度分级（Critical/High/Medium/Low）
4. 逐一修复

### 5.3 注意点

- 原型是**参考**不是**模板** — 样式可以改进，布局和交互应保持一致
- 原型可能缺少某些页面（如登录页）— AI 应自行补充
- 原型可能使用了 emoji 图标 — 可以用 Lucide 图标替代，保持视觉一致性

## 六、记忆系统

### 6.1 为什么需要

AI 每次对话没有历史记忆（除非开启记忆功能）。把关键信息存入记忆文件，可以让 AI 在未来的对话中自动调取，避免重复解释。

### 6.2 存储什么

| 类型 | 例子 | 原因 |
|------|------|------|
| 用户偏好 | "我偏重前端UI细节" | AI可以据此调整回答风格 |
| 决策记录 | "选择了shadcn/ui而非Ant Design" | 避免将来重新讨论 |
| 踩坑经验 | "type=button防止滚动到顶部" | 避免再次踩坑 |
| 项目状态 | "一期范围：合约主线" | AI知道当前聚焦什么 |
| 代码规范 | "禁用硬编码颜色" | AI自动遵守规则 |

### 6.3 记忆文件示例

```markdown
---
name: sidebar-accordion-behavior
description: 侧边栏手风琴菜单的完整交互规范
metadata:
  type: feedback
---

侧边栏使用手风琴（accordion）交互模式，具体规则：
...

**Why:** 用户多次反馈侧边栏交互问题，经过多轮修复形成此规范。
**How to apply:** 修改或新增sidebar组件时遵循上述规则。
```

## 七、总结

### 适合 AI 辅助开发的特点

| 场景 | 适合度 | 说明 |
|------|--------|------|
| 从0到1搭建项目 | ✅ 非常适合 | AI能快速生成脚手架和完整的代码框架 |
| UI 还原原型 | ✅ 非常适合 | AI能阅读HTML原型并还原为React组件 |
| 批量修复问题 | ✅ 非常适合 | AI能做系统性扫描和批量修改 |
| 文档编写 | ✅ 非常适合 | AI能保持格式统一、内容完整 |
| 复杂业务逻辑 | ⚠️ 需要人工把关 | AI生成的业务逻辑需要 review |
| 高精度UI微调 | ⚠️ 需要多轮迭代 | pixel-perfect 需要用户反馈修正 |

### 人机分工

```
用户负责                    AI 负责
───────                    ───────
产品方向                   代码实现
需求定义                   方案调研
验收确认                   文档撰写
纠偏反馈                   问题排查
风格判定                   重复性工作
```
