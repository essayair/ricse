# 业务单元、权限与审批优化方案

> 状态：一期核心能力已开发，P1 精细化能力待后续迭代
> 决策日期：2026-09-15
> 关联规范：[权限与数据范围规范](./权限与数据范围规范.md)

## 一、背景与目标

平台业务存在按地区、商品、项目或综合业务划分的大业务部。这些业务组织承担经营责任，原则上对应利润中心；同一员工可以参与多个业务组织，不同业务组织可以配置不同责任人。

本次迭代引入统一的“业务单元”概念，解决以下问题：

- 玉门、龙游等业务由同一运营主管统筹，但由不同业务责任人审批；
- 不同业务单元的责任人只能查看和处理本单元数据；
- 同一账号可以参与多个业务单元，并在不同单元承担不同职责；
- 合同确定业务归属后，下游履约、库存和结算数据保持同一归属；
- 审批流程复用同一模板，根据合同业务单元动态匹配审批人；
- 收口普通用户只读访问、外部企业授权及菜单按钮权限不一致的问题。

## 二、统一术语

| 概念 | 定义 | 示例 |
|---|---|---|
| 业务部门 | 员工行政组织归属 | 运营部、财务部 |
| 业务单元 | 承担经营、利润、数据和审批责任的大业务组织 | 玉门业务单元、龙游业务单元 |
| 利润中心 | 业务单元对应的财务核算属性 | `PC-YM`、`PC-LY` |
| 角色 | 决定用户可以执行哪些操作 | 运营经理、业务责任人、风控/财务经理 |
| 数据范围 | 决定角色可以在哪些数据上执行操作 | 指定业务单元、本企业、全部数据 |
| 审批流程 | 定义节点顺序、节点角色、人员范围、条件和审批方式 | 运营审核 → 业务确认 → 风控审批 |

产品界面统一显示“业务单元（事业部）”，底层模型及技术字段继续使用 `BusinessUnit/businessUnit`。不再以“业务组”承载经营责任。业务单元（事业部）可以按区域、产品、项目或综合口径设置，并记录利润中心编码。

### 三类主体必须分开

| 维度 | 解决的问题 | 系统记录 | 示例 |
|---|---|---|---|
| 平台管理主体 | 部门、员工、账号和事业部由谁管理 | `Company.isManagementEntity` | 和光云链运营组织 |
| 业务单元（事业部） | 业务由哪条经营线负责、谁能看、谁审批、利润归哪 | `businessUnitId` | 玉门事业部、龙游事业部 |
| 法律/货权主体 | 谁签合同、谁拥有库存、谁应收应付 | `signingPartnerId` / `ownerPartnerId` | A 公司、B 公司 |

三者相互关联但不能互相替代。内部业务公司可以只在合作伙伴主数据中作为签约和货权主体存在，不因增加一个签约主体就自动增加一套事业部。合同组合允许为“玉门事业部 + A 公司签约”，也允许为“玉门事业部 + B 公司签约”。

## 三、核心规则

1. 一个用户账号可以归属多个业务单元，并设置一个默认业务单元。
2. 一个业务单元可以包含多名用户，并配置多个岗位角色。
3. 用户归属业务单元不自动获得操作权限；实际权限由“角色 + 该角色适用的业务单元”共同决定。
4. 一份合同必须归属一个主业务单元。其他地区、品类和项目属性可以作为统计标签，但不作为一期权限主键。
5. 合同下游单据自动继承业务单元，不允许各环节独立修改造成归属漂移。
6. 审批节点绑定通用角色，不为玉门、龙游分别创建重复角色或重复流程。
7. 审批提交时按照“合同业务单元 + 节点角色”动态匹配人员，并固化本轮审批人快照。
8. 权限判断必须把功能权限与其所属授权范围绑定计算，禁止先分别取并集再交叉组合。
9. 业务单元不随合同签约主体切换；签约主体不决定人员权限范围。
10. 库存必须同时区分业务单元、货权主体、仓库、物料和批次，不允许跨业务单元或跨货权主体自动调剂。

授权判断统一为：

```text
账号、员工和企业有效
  AND 某一有效角色包含目标操作权限
  AND 该角色的授权范围覆盖目标合同业务单元
  AND 当前单据状态允许该操作
```

## 四、业务单元管理

### 4.1 基础字段

| 字段 | 规则 |
|---|---|
| 系统 ID | 系统自动生成的 `cuid`，仅用于数据库关联，不允许人工填写或修改，业务页面默认不展示 |
| 业务单元编码 | 系统按 `BU-{平台管理主体编码}-{三位流水号}` 自动生成，全局唯一，创建后不可修改 |
| 业务单元名称 | 必填且允许修改，例如“玉门事业部”；改名不改变编码及历史业务关联 |
| 单元类型 | 区域型、产品型、项目型、综合型 |
| 平台管理主体 | 系统固定带入，承载组织管理关系；不表示合同签约或库存货权主体 |
| 上级业务单元 | 可选，用于形成管理层级 |
| 业务负责人 | 可选展示字段；审批资格仍以角色授权为准 |
| 利润中心编码 | 可选，一期原则上一业务单元对应一个利润中心 |
| 状态 | 启用、停用 |
| 说明 | 可选 |

停用业务单元后不允许新合同选择，历史合同和报表仍保留原归属。现有历史编码保持不变，新建数据开始执行自动编号规则。

初始化规则：空白系统创建第一家内部组织企业时，将其设为唯一的平台管理主体，并自动生成一个“综合事业部”；后续增加内部签约主体或组织企业时不再自动创建事业部。综合事业部名称允许修改，系统 ID 和编码不变。

### 4.2 用户归属

账号管理增加：

- 所属业务单元：多选；
- 默认业务单元：从已选业务单元中单选；
- 生效时间、失效时间和状态；
- 用户角色授权时，只能从其所属业务单元中选择适用范围。

“所属业务单元”表示参与关系，不直接授予查看、修改或审批能力。一个用户在不同业务单元可以拥有不同角色。

示例：

| 用户 | 所属业务单元 | 角色授权 |
|---|---|---|
| 运营主管 | 玉门、龙游 | 运营主管：玉门 + 龙游 |
| 玉门负责人 | 玉门 | 业务责任人：玉门 |
| 龙游负责人 | 龙游 | 业务责任人：龙游 |
| 跨区协作人员 | 玉门、龙游 | 业务责任人：玉门；普通查看：龙游 |

授权页面应检测更大范围授权。例如用户已通过其他角色获得本企业全部合同查看权限时，应提示该授权会突破业务单元隔离预期。

## 五、合同及下游数据归属

合同增加必填字段“业务单元”：

- 创建人只有一个有效业务单元时自动带入；
- 有多个业务单元时默认带入默认业务单元，并允许从授权范围内切换；
- 草稿状态允许修改；
- 审批中必须先撤回再修改，并重新生成审批人员；
- 已审批或执行中的合同不能直接修改，后续通过受控的“业务归属调整”操作处理并留痕。

下游继承链：

```text
合同（业务单元）
  → 执行批次
  → 执行通知
  → 物流运单
  → 磅单 / 质检
  → 入库 / 出库
  → 库存批次 / 库存台账
  → 结算 / 发票 / 收付款
```

下游表可以按查询和报表需要冗余业务单元 ID，但必须由系统从来源单据写入，禁止前端任意选择；合同仍是最终归属依据。

库存最小隔离口径为：

```text
业务单元（事业部） + 库存货权主体 + 仓库 + 物料 + 库存批次
```

例如龙游事业部和玉门事业部都用 A 公司采购 97 萤石粉，即使货物放在同一仓库，也形成两组独立库存。销售冻结、生产领料和出库批次分配必须同时匹配业务单元与货权主体；库存总览可以向上汇总，但汇总数不能直接用于跨单元出库。

未来结算单必须同时固化业务单元和法律主体：业务单元用于利润分析与内部责任，法律主体用于应收、应付、发票和收付款，二者不得合并为一个字段。

## 六、审批流程

### 6.1 节点配置

审批流程继续按合同类型、金额等条件选择模板。节点至少配置：

| 配置项 | 说明 |
|---|---|
| 节点名称 | 运营审核、业务确认、风控审批等 |
| 节点角色 | 必须是拥有合同审批权限的有效角色 |
| 人员范围 | 合同业务单元、合同所属企业、指定业务单元、全平台 |
| 审批方式 | 或签、会签 |
| 节点条件 | 始终执行、达到金额阈值等 |
| 顺序与状态 | 节点顺序、启用、停用 |

典型流程：

```text
玉门合同：运营经理（玉门范围） → 风控/财务经理（全平台） → 玉门业务责任人 → 总经理
龙游合同：运营经理（龙游范围） → 风控/财务经理（全平台） → 龙游业务责任人 → 总经理
```

采购、销售和双边合同一期统一使用上述四级流程，默认均为或签，不再按合同金额省略总经理节点。运营经理和业务责任人使用 `BUSINESS_UNIT` 范围；风控/财务经理和总经理使用 `ALL` 范围。

同一个人同时匹配连续两个节点时，一期仍生成两个独立审批任务，分别记录审批意见和职责，不自动跳过。

### 6.2 提交与变更

合同提交前必须展示审批路径预览，包括节点、角色、范围、审批方式和预计审批人。任一节点没有有效人员时阻止提交，并明确提示缺少人员的业务单元和角色。

提交后保存流程版本和审批人员快照。后续调岗、停用或修改角色不应静默改变已在途审批；确需换人时使用管理员转交或重新发起并保留审计记录。

## 七、菜单、按钮和接口权限

### 7.1 普通业务用户

- 预置普通业务角色可以获得工作所需模块的查看权限；
- 拥有模块查看权限时显示对应菜单、列表和详情；
- 没有新增、修改、删除、确认、作废、过账或审批权限时，隐藏对应操作入口；
- 页面隐藏仅用于改善交互，后端仍必须逐接口校验；
- 数据列表、详情、数量统计、附件和候选单据使用同一业务单元范围。

禁止把“菜单可见”作为授权依据，也禁止出现只隐藏按钮但接口仍可调用的情况。

### 7.2 外部企业账号

试运行阶段采用业务权限白名单：

- 仅按实际协作需要授予合同、物流、磅单、质检、出入库等查看或操作权限；
- 不开放主数据管理、组织管理、用户管理、角色权限和审批流程配置；
- 不显示主数据、组织数据和系统管理菜单；
- 业务表单需要的物料、地址、车辆等选项通过受限候选接口提供，不因此开放全量主数据接口；
- 数据范围继续固定为本企业作为合同参与方产生的关联业务数据。

外部企业专属主数据只读视图和字段脱敏完成后，再评估开放相应只读能力。

## 八、现有不足与本次收口范围

| 问题 | 风险判断 | 处理优先级 | 目标处理方式 |
|---|---|---|---|
| 缺少业务单元权限边界 | 无法满足多业务责任人隔离 | P0 | 建立业务单元、用户归属、合同归属和范围继承 |
| 功能权限与数据范围分别取并集 | 多角色不同范围时可能发生权限范围放大 | P0 | 按授予目标权限的角色计算对应数据范围 |
| 普通业务菜单未全面按权限控制 | 易出现看得到入口但操作报错 | P0 | 菜单按查看权限，按钮按操作权限，后端二次校验 |
| 外部账号可能获得不必要的基础权限 | 可能暴露平台主数据和组织信息 | P0 | 外部账号白名单及受限候选接口 |
| 主数据、组织数据缺少外部专属只读视图 | 不适合直接开放外部访问 | P1 | 建设字段脱敏、企业专属视图和范围测试 |
| 多数模块只有 `view/manage` 两级 | 不能单独限制删除、确认、过账等高风险动作 | P1 | 优先拆分删除、确认、过账、冲销等高风险权限 |
| 角色与审批配置接口仍强制管理员 | 已有权限编码不能真正委派 | P1 | 统一采用明确权限守卫；是否委派由角色配置决定 |
| 前端授权信息刷新不统一 | 修改授权后可能需要重新登录 | P1 | 登录外壳加载最新个人权限，授权变更后主动刷新 |
| 角色管理页面不完整 | 新增、编辑和停用仍不便 | P1 | 补齐角色配置页面并保留系统角色保护 |

## 九、实施顺序

截至 2026-09-15，阶段一至阶段三的核心数据模型、账号配置、合同归属、范围继承、动态审批和 Web 端配置入口已经完成；小程序工作台、审批、业务查询和现场任务已同步展示业务单元归属并实时继承后台授权。移动端业务单元显式切换、审批转交和更细操作权限列入阶段四。

### 阶段一：权限安全收口（P0）

1. 权限与数据范围改为同一角色授权内计算；
2. 外部账号应用业务权限白名单；
3. Web 与小程序统一菜单、按钮和后端权限映射；
4. 增加越权、跨单元、附件和候选接口测试。

### 阶段二：业务单元基础（P0）

1. 建立业务单元及用户多选归属；
2. 增加默认业务单元和角色适用范围；
3. 合同增加业务单元并完成历史数据归属；
4. 下游业务查询、统计和附件继承业务单元范围。

### 阶段三：审批动态选人（P0）

1. 审批节点增加合同业务单元范围；
2. 提交前预览实际审批人；
3. 提交时固化流程版本与审批人快照；
4. 增加无人审批、多人或签/会签、同人多节点和跨单元测试。

### 阶段四：权限精细化（P1）

1. 拆分高风险操作权限；
2. 补齐角色及审批配置页面；
3. 完成外部企业专属只读视图和字段脱敏；
4. 实现授权实时刷新和完整审计查询。

## 十、历史数据迁移

- 初始化仅为唯一的平台管理主体建立一个“综合事业部”，后续内部签约主体不自动创建；
- 既有多个内部企业下的业务单元统一迁到平台管理主体，编码与历史关联保持不变；
- 历史合同必须由管理员批量分配业务单元，不允许长期为空；
- 历史下游数据通过合同链回填或动态继承业务单元；
- 历史入库、库存批次、库存台账、出库管理单、销售出库单和生产任务按合同来源或创建人默认单元回填；无法判断的记录列入“未归属业务单元”清单，不自动猜测；
- 现有单值 `businessGroupId` 不继续作为新权限依据，迁移为用户与业务单元多对多关系；
- 现有部门、企业和本人范围继续保留，与业务单元范围并行；
- 上线迁移前生成未归属合同、无默认业务单元用户、无审批责任人的检查清单；
- 迁移和授权变更必须记录操作人、时间及变更前后内容。

## 十一、验收口径

- 一个账号可以勾选多个业务单元，并设置唯一默认业务单元；
- 用户只能为角色选择其本人已归属的业务单元；
- 玉门责任人无法查看、检索、导出或通过 URL 访问龙游合同及附件；
- 运营主管同时覆盖玉门、龙游时，可以查看和审批两地业务；
- 用户在玉门有审批权限、在龙游只有查看权限时，不能审批龙游合同；
- 合同创建时正确默认业务单元，提交前可以预览实际审批人；
- 下游单据、首页统计、移动工作台和附件均继承相同业务单元范围；
- 同一业务单元可选择不同内部签约主体，同一内部签约主体也可服务多个业务单元；
- 同仓同货权主体同物料但业务单元不同的库存不能相互冻结、领料或出库；
- 只有查看权限的用户看不到写操作按钮，直接调用写接口返回无权限；
- 外部账号看不到主数据、组织和系统管理入口，也不能调用对应管理接口；
- 授权修改后前端及时刷新，后端立即按最新授权执行。

## 十二、一期暂不建设

- 多个业务单元共同拥有同一合同；
- 复杂矩阵组织的比例分摊；
- 一个合同金额拆分到多个利润中心；
- 可视化 BPM、任意脚本条件和复杂并行网关；
- 自动跳过同一审批人的连续节点。
