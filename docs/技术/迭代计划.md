# 迭代计划

> 版本：v2.0 | 日期：2026-07-27
>
> 本项目采用**小步迭代**策略。每次迭代包含完整的 DB → API → 前端 → 测试链路，
> 产出可独立验证的功能。不追求一次性铺开所有模块。

---

## 迭代原则

1. **每次迭代可验证** — 迭代结束时，新增功能可在 UI 上操作、可用 API 调用、测试通过
2. **DB 先行** — 每次迭代先确定数据模型变更，再写 API，最后做前端
3. **不超前设计** — 不为未来可能的需求预留字段或抽象，当下需要什么就加什么
4. **文档随代码走** — 每次迭代如果发现文档缺失或过时，同步更新
5. **验收门槛** — API 可用（curl 验证） + 前端可操作 + 至少一个测试用例

---

## 依赖顺序

```
认证/权限 ─→ 主数据 ─→ 合同 ─→ 审批 ─→ 执行批次 ─→ 执行通知
                                                      ↓
物流运单 ─→ 磅单 ─→ 质检 ─→ 物流出入库 ─→ 库存/冲销 ─→ 结算

测试与数据范围校验贯穿所有模块
```

**为什么主数据排在第二位？**

所有业务单据都依赖主数据和统一权限范围：
- 合同依赖**供应商**和**物料**
- 执行批次依赖**物料**和**合作伙伴**
- 结算依赖**合同**和**供应商**
- 车辆、仓库、人员是物流/库存/审批的前置条件
- 下游单据通过来源关系继承合同参与企业范围

所以 Iteration 1 认证、Iteration 2 主数据完成后，后续业务迭代才有数据可用。

## 迭代节奏

- 一次做一个迭代，做完验证通过后 commit
- 一个迭代 1-3 天（视复杂度）
- 每次迭代结束，更新 `docs/更新记录.md`
- 如果迭代中发现设计缺陷，先更新模块设计文档，再改代码
