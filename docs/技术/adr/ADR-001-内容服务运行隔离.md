# ADR-001: 内容服务与核心交易服务运行隔离

## 状态

已接受

## 日期

2026-08-20

## 背景

官网、小程序的资讯同步、百川行情下载、Excel 解析和 DeepSeek 清洗当前运行在同一个 `fyzs-server` 进程中。迁入 RICSE 后，如果继续与合同、库存、审批和物流运行在同一 API 进程，第三方超时、长连接、CPU/内存突增或进程崩溃会扩大为核心交易故障。

代码统一到 RICSE 是仓库治理要求，但不等同于必须使用一个运行进程。

## 选项

- 选项 A：所有功能运行在同一 RICSE API，仅增加超时、限流和熔断。实施简单，但进程级故障无法隔离。
- 选项 B：交易/内容共用 API，后台任务单独 Worker。可隔离批处理，但实时 AI 和公开内容流量仍与交易 API 争用资源。
- 选项 C：`core-api`、`content-api`、`content-worker` 三进程，同仓库、同流水线、共享基础设施并逻辑隔离数据。
- 选项 D：内容服务使用独立服务器和独立数据库。隔离最强，但当前运维成本过高。

## 决策

采用选项 C。

- `core-api` 只承载合同、审批、物流、库存、生产等核心业务。
- `content-api` 承载内容后台、公开查询、微信登录、行情和实时 AI。
- `content-worker` 承载资讯同步、批量 AI、行情采集和文件解析。
- 三个进程代码均位于 RICSE 仓库，通过 Docker 独立部署和健康检查。
- 当前共享 PostgreSQL、Redis 和 MinIO，但使用独立表、队列、连接池和对象前缀。

## 影响

正面：

- 第三方服务故障不再导致核心交易 API 重启。
- 内容 API 和 Worker 可独立暂停、扩容、限流和发布。
- 保持单仓库、统一类型、统一发布记录和低运维复杂度。

负面：

- Docker Compose、Nginx、健康检查和流水线增加两个运行单元。
- 共享数据库和同主机仍存在资源争用，需要连接池和容器资源上限。
- 模块必须遵守边界，内容服务禁止直接写核心交易表。
