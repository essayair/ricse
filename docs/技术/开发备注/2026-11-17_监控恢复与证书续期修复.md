# 监控恢复与证书续期修复

## 背景及根因

用户授权继续处理线上证书与监控平台配置。只操作既有ECS，不部署本地尚未提交的交易业务改动，不重建业务数据。

1. API域名证书于2026-11-15过期；官网证书2026-11-18将到期。
2. 既有Certbot全局pre-hook会停Nginx，而API/官网使用webroot验证，导致ACME无法读取验证文件。日志明确为Connection refused。RICSE/大屏使用standalone，与webroot混合在一次renew中运行造成冲突。
3. 线上监控平台记录 `mplat_ezviz` 存在，但处于INACTIVE且appKey/appSecret为空；原4组、21个监控点位仍在。本地开发库没有平台记录，不擅自将生产凭据复制到开发数据库。
4. 大屏旧页只定时抓拍，双击后才创建播放器，不是四路实时自动播放。

## 线上已执行

- 用已有Certbot账户、原验证目录、正常TLS流程续期API与官网证书至2027-02-15；`nginx -t`后平滑reload，没有关闭证书校验。
- 从旧版受信任大屏Git配置提取既有萤石凭据，只通过SSH stdin传入服务端；先向官方 `open.ys7.com` 验证成功，再事务恢复唯一空白停用的平台，保留全部点位与其他数据。
- 凭据未写入临时脚本、命令参数、日志或新Git文件；未复制到开发库。运维恢复以管理员账号记录 `RESTORE_CONFIG`，details注明授权SSH维护、来源、已验证及点位不变，不含密钥。
- 既有旧代码历史中仍可能含原凭据，后续建议按维护计划轮换；本次未擅自轮换导致其他客户端失效。
- 服务器安装 `/usr/local/sbin/ricse-safe-cert-renew` 与 `/usr/local/libexec/ricse-cert-deploy`；现有 `certbot-renew.timer` 继续启用，通过systemd drop-in改用安全入口。原服务配置快照存服务器 `/opt/ricse/backups/cert-maint-20261117/`。

## 续期实现

- `deploy/certbot/safe-renew.sh` 按每份renewal配置单独调用Certbot，用 `--no-directory-hooks` 禁用冲突的全局停站钩子。
- webroot/nginx验证不加停站钩子；standalone仅为自身调用明确的pre/post停启，后续证书在独立进程中执行，不会被前一张的停站状态影响。
- 显式deploy-hook仍执行RICSE证书复制；Nginx运行时验证并reload，standalone停站时由post-hook启动后加载新证书。
- 失败保留非零退出供systemd告警，继续检查其他证书。未来主机发布也会安装入口和drop-in，避免发布覆盖后复发。
- 回归：`bash deploy/tests/certbot-safe-renew.test.sh`，验证webroot不停、standalone隔离、dry-run透传与失败反馈；Shell语法检查通过。
- 线上 `certbot-renew.service` 实际运行结果为success、退出0；API证书官方测试环境dry-run续期成功，Nginx持续active。生产证书未被测试证书替换。
- 操作依据：[Certbot官方续期与钩子说明](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates)。服务器为Certbot1.22，采用现有版本支持的renew参数，不假设存在新版reconfigure命令。
