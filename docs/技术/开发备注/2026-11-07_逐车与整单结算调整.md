# 逐车与整单结算调整

日期：2026-11-07。范围：采购、销售实际货物结算（GOODS），不改变运费及历史合同阶段结算模型。

## 业务与交互

1. 逐车数量、含税每吨单价使用显式勾选；两者互斥。切换提示恢复另一项，要求调整说明。品位合同按原规则命中元/度价，再换算含税每吨参考价；人工调价不改合同或检测报告。
2. 明细合计下新增最终结算：按明细、调整总干基、调整总金额三选一。整单调整不与逐车人工数量、价格或历史加减项叠加。切换前确认，取消不丢失原值。
3. 总干基调整仅适用于单一合同物料、相同合同含税单价和每吨扣款的干基货物。金额随数量同步重算，质量扣款同步；不同品位价格或多物料改用逐车调整。不允许修改总实物数量。
4. 总金额调整保持明细不变，在单头反映差额。两种整单调整都须说明，不把差额回摊车辆，不改库存或源单据。
5. 顶部及底部汇总使用最终值；详情、预览和打印同时展示明细合计与最终结算。付款和发票对账继续使用单头最终数量、金额。

## API 与持久化

- 新增 `lines[].adjustedUnitPrice`（含税元/吨，4 位小数）与 `settlementAdjustment: { mode, quantity?, amount?, reason? }`。数量 3 位，金额 2 位，使用 Prisma.Decimal 计算。
- `goods-settlement-adjustment.ts` 统一采购销售计算。原 `unitPrice` 校验及 `adjustmentAmount` 仅作兼容，不用旧金额字段承载新单价调整。
- 每行 `sourceSnapshot.lineAdjustment` 保存原数量、合同含税单价、最终单价、每吨扣款、可协商上限及调整原因。首行 `sourceSnapshot.settlementAdjustment` 保存版本、调整方式、明细基线、最终值、差额和原因，避免同一调整重复计入。
- 单头保存最终值，行记录保留逐车事实。合同溢短装累计将首行整单数量差额计入一次；运单占用不因少结数量解除，不允许按差额重复结算。
- 确认结算及后续付款来源校验重新核对最终值与快照，防止只改头部金额绕过计算；原磅单、检测报告版本核对继续执行。
- 人工调价、整单调整纳入既有审批判定及签章依据校验；溢短装本身仍沿用原线下签章确认机制。
- 无新数据库列，无迁移。历史无版本快照的已存单据不追溯重算。历史草稿加减项原样带出，仅允许主动取消，不静默转为单价。

## 验证重点

- 采购、销售的预览和保存使用相同计算；整单数量变化不改逐车行。
- 同一车数量与单价互斥；整单数量与金额互斥；逐车与整单互斥，前后端双重校验。
- 质量扣款、含税价格、品位分档及回收率扣款保留原逻辑；多价格不得套统一干基公式。
- 调整说明、计量上限、金额正数、持久化核对、累计数量与历史兼容均纳入单元测试。

## 本次验证结果

- 前后端 TypeScript 类型检查通过；结算模块 12 个测试套件、125 项测试通过；前端依据选择、汇总及物流结算筛选 20 项测试通过。
- 本地浏览器验证总干基 1040.612 → 1040.000 吨，单价 2920 元/吨时同步得到 3,036,800.00 元，逐车明细不变；预览展示明细及最终两行。
- 验证整单金额调整、取消切换保留输入、逐车与整单切换恢复、同车数量与单价互斥。仅试算和预览，未保存测试单据或触发付款。
