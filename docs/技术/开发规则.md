# 开发规则.md

> 编码规范、DDD 分层约定、命名规范、提交规范。所有 AI 产出和人工代码须遵守。

---

## 一、DDD 分层约定

### 1.1 每模块内部四层结构

```
modules/{module-name}/
├── domain/          # 领域层：实体、值对象、领域服务、状态机
├── application/     # 应用层：命令/查询处理器、DTO
├── infrastructure/  # 基础设施层：Repository 实现、外部 API 适配器
└── interfaces/      # 接口层：Controller、API 路由
```

### 1.2 禁止跨模块直接访问

- ✅ 允许：通过应用服务调用或领域事件
- ❌ 禁止：跨模块直接访问对方 Repository 或数据库表

### 1.3 模块间通信

- **同步**：应用服务调用（同进程，无网络开销）
- **异步**：领域事件总线（EventEmitter），如合同生效 → 通知物流

## 二、代码规范

### 2.1 命名

| 类型 | 规范 | 示例 |
|------|------|------|
| 类 | PascalCase | `ContractService`, `CreateContractDto` |
| 函数/方法 | camelCase | `createContract()`, `findById()` |
| 变量 | camelCase | `contractStatus`, `totalAmount` |
| 常量 | UPPER_SNAKE | `CONTRACT_STATUS`, `MAX_AMOUNT` |
| 文件 | kebab-case | `create-contract.dto.ts` |
| 路由 | kebab-case | `POST /api/v1/contracts` |
| 数据库字段 | snake_case | `contract_status`, `company_id` |
| TypeScript 枚举 | PascalCase | `enum ContractStatus { DRAFT, PENDING }` |

### 2.2 文件命名映射

```
contract.service.ts         # 服务
create-contract.dto.ts      # DTO
contract.entity.ts          # 实体/模型
contract.controller.ts      # 控制器
contract.repository.ts      # Repository
contract.state-machine.ts   # 状态机
```

### 2.3 Prisma Schema

- 所有核心业务表包含 `deleted_at`（软删除）
- 新业务模型必须能够通过直接字段或来源单据关系追溯合同/企业范围
- 主数据使用版本化管理（`version` + `effective_from`/`effective_to`）
- 禁止手动 DDL，结构变更一律走 `prisma migrate`

### 2.4 权限与数据范围

- Controller 必须传入当前用户 ID，Service 负责功能权限与数据范围校验。
- 禁止只在前端隐藏按钮，所有写操作必须在后端校验对应 `资源.操作` 权限。
- 列表、详情、候选单据、状态操作和附件接口必须使用同一范围来源。
- 外部企业业务范围必须沿合同参与方及来源单据继承，禁止退化为 `createdBy` 过滤。
- 新增结算、发票、收付款模块前，先在 `AccessControlService` 定义对应 Prisma 范围构造器。
- 跨范围详情统一按不存在处理或明确拒绝，禁止返回无权单据的存在性和敏感字段。
- 具体口径见 `模块设计/角色权限与数据范围.md`。

## 三、数据库管理两条铁律

> 写入即强制执行，违反视为事故。

1. **禁止手动 DDL**——生产环境严禁人手连库改表/改结构。结构真相在 `schema.prisma`，手改会导致代码与库不一致、下次迁移冲突。结构变更只走 Prisma migrate。
2. **数据访问收口 Repository**——禁止跨模块直接访问对方表，所有库操作经本模块 Repository 层。

## 四、Git 规范

### 4.1 分支策略

- `main` — 生产就绪，始终可部署
- `feat/*` — 功能分支，从 main 切出
- `fix/*` — 修复分支
- `db/*` — 数据库迁移/Prisma
- `docs/*` — 文档变更

### 4.2 提交信息格式

```
{prefix}: {简短描述}

{详细说明（可选）}

前缀：feat | fix | docs | refactor | chore | db | ai
```

### 4.3 提交前检查

- [ ] TypeScript 无类型错误（`tsc --noEmit` 通过）
- [ ] 单元测试通过
- [ ] Prisma Schema 变更已生成迁移
- [ ] 符合 DDD 分层约束（无跨模块直接访问表）
- [ ] 涉及 UI 库组件时，符合 shadcn/ui 命名惯例

## 五、API 规范

### 5.1 URL 命名

```
GET    /api/v1/{resources}          # 列表（分页+筛选）
GET    /api/v1/{resources}/:id      # 详情
POST   /api/v1/{resources}          # 创建
PUT    /api/v1/{resources}/:id      # 全量更新
PATCH  /api/v1/{resources}/:id      # 部分更新
DELETE /api/v1/{resources}/:id      # 软删除
PATCH  /api/v1/{resources}/:id/status  # 状态流转
```

### 5.2 统一响应格式

```typescript
interface ApiResponse<T> {
  code: number;
  message: string;
  data: T;
  requestId: string;
}
```

### 5.3 分页响应

```typescript
interface PaginatedResponse<T> {
  items: T[];
  meta: { page: number; pageSize: number; total: number; totalPages: number };
}
```

## 六、状态机约定

- 每个有状态流转的业务对象，在 domain 层定义状态转换表
- 状态转换表格式：

```typescript
interface StateTransition {
  from: Status;
  to: Status;
  condition?: (entity) => boolean | Promise<boolean>;
  sideEffect?: (entity) => Promise<void>;
  allowedRoles: string[];
}
```

- 状态机在前端只读展示，状态变更**必须经后端校验**
- 一期不做通用 BPM 引擎，审批流在代码里写死

## 七、AI 协作约定

### 7.1 自动执行范围

以下操作 AI 可无需确认直接执行：
- 创建/修改代码文件（符合开发规则）
- 运行 `pnpm install` / `npm install`
- 运行 `prisma generate` / `prisma migrate dev`
- 运行测试
- 创建/修改文档（docs/ 目录）
- git add / git commit

### 7.2 需人工确认

以下操作 AI 必须经用户确认后才能执行：
- git push（尤其是 force push）
- 修改生产环境配置
- 修改数据库连接字符串
- 删除文件/目录
- 修改 Sot.md 中的锁定决策

### 7.3 Prompt 归档规则

- 有效 prompt 保存到 `docs/prompt记录/`
- 文件名格式：`{日期}_{场景}.md`
- 内容包含：prompt 全文 + 产出质量评估 + 可复用说明
