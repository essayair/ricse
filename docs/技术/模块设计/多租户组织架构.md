# 多租户组织架构与主数据管控需求设计

---

## 平台定位与组织体系

### 1.1 平台角色

- **平台运营方**：作为区域产业链的服务平台，全面管理平台的所有业务流程、运营全局数据。

- **通道贸易商**：深度参与产业链大宗贸易，作为"贸易通道"链接上下游的外部供应商和客户，内部存在多个独立核算的法人实体。

### 1.2 编码与组织规则

- **内部企业（自营主体）**：由于采用多法人实体运作，内部企业拥有多个，系统内统一采用 **6位编码**（如 `100000`, `200001`），在交易中兼具客户与供应商属性。支持数字或者字母。

- **外部合作伙伴（往来单位）**：包含上游供应商、下游客户、三方服务商等，系统内统一采用 **8位数字编码**（如 `80000001`）。仅仅支持数字。

- **行政组织与业务解耦**：内部员工行政关系统一挂靠在虚拟的"平台运营总部"树状图下，**不与医社保等具体法律/人资关系强绑定**，确保人员跨法人操作和切换的灵活性。

- **外部组织架构（未来规划）**：未来支持外部企业通过组织数据建立自身的组织架构树，并在其企业主体下自主添加员工账号（子账号）。

## 组织 → 用户 → 权限：完整链路

用户与权限不应作为独立的主数据模块，而是挂在组织数据之下。完整链条为：

```
企业（Company）
  └── 部门（Department）
        └── 员工（Employee）
              └── 开通账号 → 用户（User）
                    └── 勾选业务组（Business Group）
                          └── 可操作指定业务线（Business Line）
```

### 2.1 内部企业用户创建流程

1. **创建企业**：在组织数据中建立内部企业（6位编码），如 `100000` 嘉溢、`200000` 业务公司
2. **建立部门**：在企业下建立部门树（如：总经办、采购部、销售部、财务部）
3. **添加员工**：在部门下添加员工记录（姓名、职位、联系方式）
4. **开通账号**：为员工开通系统登录账号（User），关联该员工
5. **分配业务组**：为用户勾选可操作的业务组 → 默认全选所有业务组（内部无限制），可按岗位手动收紧
6. **操作业务**：用户只能看到和操作其业务组关联的内部企业下的业务单据

### 2.2 外部企业用户创建流程（一期：运营代建）

1. **创建合作伙伴**：运营在合作伙伴管理中录入外部企业，生成 8 位编码
2. **建立企业主体**：系统自动或手动在组织数据中建立外部企业记录（引用合作伙伴编码）
3. **开通管理员账号**：运营在「用户管理」中为该外部企业创建管理员账号（最多 6 名）
4. **自动绑定**：外部企业管理员账号创建时，`company_id` 自动绑定其所属外部企业，业务组默认仅包含该企业
5. **默认隔离**：外部用户登录后，**默认只能查看和操作本企业作为买卖方的业务单据**

> **流程解耦要求**：外部企业管理员账号**禁止**在录入合作伙伴的表单中直接创建，必须切换到独立的用户管理模块操作。

### 2.3 业务组机制

系统支持创建逻辑"业务组"，业务组作为权限隔离的桥梁：

- 每个业务组直接关联一个或多个 **6 位内部企业代码**
- 内部用户：默认勾选全部业务组（无限制），可按岗位收紧
- 外部用户：仅勾选其所属企业对应的业务组（严格隔离）
- 拦截：若取消所有业务组勾选，系统提示"必须至少归属于一个业务组"

## 账户与数据权限规则（内外双轨制）

### 3.1 内部用户权限

| 维度 | 规则 |
|------|------|
| 默认权限 | 全业务组放开，无数据隔离 |
| 收紧方式 | 管理员手动取消业务组勾选 |
| 安全要求 | 至少保留一个业务组 |
| 一期策略 | 粗粒度：所有内部用户全量可见 |

### 3.2 外部用户权限

| 维度 | 规则 |
|------|------|
| 默认权限 | 仅本企业业务数据 |
| 数据范围 | 本企业作为买方/卖方的合同及关联单据 |
| 系统隔离 | `company_id` 硬编码，不可切换 |
| 账号名额 | 单企业最多 6 名管理员 |

## 业务单据与多级供应链穿透

### 4.1 自主创单与标签化存储

- 外部合作伙伴获得账号后，可以自主在平台创建属于自己的业务合同以及后续的流转单据（如订单、送货单等）。

- 任何业务单据在创建入库时，系统必须在底层自动且不可逆地写入"干系人实体标签"。数据结构必须包含：`Buyer_Company_ID`（买方ID）、`Seller_Company_ID`（卖方ID）及 `Created_By`（创建人ID）。

### 4.2 动态网络穿透与隐私控制

- **多级网络穿透**：单据链条支持网状共享。只要业务单据的"干系人映射表"中包含了某家外部企业（如被合同指派的三方物流商、次级供应商）的 8 位编码，该企业员工获得账号登录平台后，即可**动态、按需查看该特定单据**（如物流单、质检单），实现区域产业链的透明化协同。

- **商业机密隐私控制**：为了保护核心商业机密，系统需支持**字段级权限控制**。非直接签约的第三方（如物流商）在穿透查看单据时，**单据中的敏感价格字段对非签约方自动隐藏**。

## 合作伙伴主数据管控及演进规划

为了保障平台早期的合规性与风控，合作伙伴（供应商/客户）的创建与外部账号的发放采用**两阶段渐进式**规划。

### 5.1 阶段一：运营强管控模式（当前上线要求）

- **代建机制**：所有外部合作伙伴的初始创建，**必须且只能由内部运营管理平台用户来操作**。合作伙伴即便开通了平台账号，一期也完全不具备"创建其他合作伙伴"的权限。

- **企业主体建档（第一步）**：运营人员在合作伙伴管理模块录入外部企业信息。系统强制以 **18位统一社会信用代码** 进行全局防重校验。通过后，系统自动由 8 位号码池派发唯一编码。

- **独立管理员账户创建（第二步）**：运营人员完成企业建档后，切换至独立的用户管理模块，针对已生成的外部企业代码，单独为该企业创建管理员账户。流程解耦，禁止在合作伙伴表单中直接创建账号。

- **账号名额限制**：系统在一期必须支持为单一外部企业主体开通**最多 6 名**管理员账户。

### 5.2 阶段二：生态自孵化模式（未来迭代规划）

- **自主申请**：外部合作伙伴自主创建、添加他们自己的合作伙伴，提交后进入平台运营审核流。

- **自动扩展（查重机制）**：若外部伙伴申请创建的企业已存在（已有 8 位码），系统不重新编码。

- **影子关系扩展**：审核通过后，系统仅在后台拓扑关系表中建立链接。在绝对隔离其历史敏感数据的前提下，仅向申请方开放对该企业专属的局部业务视图。

## 系统开发与项目迭代策略（研发高压线）

### 6.1 一期（MVP版本）开发策略

- **权限粗粒度放行**：一期为了追求最高效率跑通主流程，允许所有内部员工操作所有业务流程，后端接口层默认不做 `company_id` 的强过滤拦截。

- **未来升级要求**：在未来迭代中，必须能通过权限角色（RBAC框架）或数据过滤器的方式，纯配置化地收紧权限并升级隔离机制，且**不能动变历史数据和重构底层表结构**。

### 6.2 架构高压线（研发硬性执行标准）

> ⚠️ **研发团队必须死守以下底层设计底线，否则不予通过架构评审：**

1. **用户与主体分离**：用户表（`sys_user`）与企业主体表（`sys_company`）必须物理分表。用户表从第一天起必须预留企业外键（`company_id`）与业务组外键（`business_group_id`）。

2. **单据归属非空**：所有业务单据表的买卖双方主键（`buyer_id` / `seller_id`）在创建写入时必须为 `NOT NULL`，严禁产生无归属实体的平台流浪单据。

3. **API URL 安全防御**：前后端单据详情等敏感接口，**严禁暴露数据库自增数字 ID**（如 `.../detail?id=1`）。必须统一采用 **UUID** 或**标准大宗业务单号**（如 `HT-20260707-0001`）进行传输，从根源杜绝未来权限收紧时被外部恶意遍历抓包（水平越权）的风险。

## 数据模型关系图（规划）

```
Company (企业)
  ├── id, code (6/8位), name, type (INTERNAL/EXTERNAL)
  ├── parentId → 行政组织树
  │
  ├── Department (部门)
  │     ├── id, name, companyId
  │     └── Employee (员工)
  │           ├── id, name, departmentId
  │           └── User (系统账号)
  │                 ├── id, username, companyId, businessGroupId
  │                 └── 通过 businessGroupId → 可操作的内部企业集合
  │
  └── BusinessGroup (业务组)
        ├── id, name
        └── BusinessGroupCompany (映射)
              ├── businessGroupId
              └── companyId → 关联内部企业
```

### 内外权限对比

| | 内部用户 | 外部用户 |
|------|---------|---------|
| company_id | 可为空（一期） | 创建时强制绑定所属外部企业 |
| businessGroupId | 默认全选 | 仅绑定所属企业对应业务组 |
| 数据可见范围 | 全部（一期粗粒度） | 仅本企业作为买卖方的单据 |
| 创建合作伙伴 | ✅ | ❌（一期） |
| 创建合同 | ✅ | ✅（仅以本企业为买卖方） |
| 子账号管理 | ✅（管理员可创建） | ✅（管理员可创建，最多 6 名） |
