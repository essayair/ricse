# 运力资源管理模块设计

> 状态：✅ 后端 + 前端（Web、移动端）均已实现。本文档记录车辆、司机、车队三类运力资源的管理方式，以及"社会运力"场景下开票承运商延迟绑定的设计。涉及 `Waybill` 的部分是对[执行通知与物流模块](./执行通知与物流模块.md)既有设计的扩展，涉及结算候选的部分是对[物流合同与结算模块](./物流合同与结算模块.md)的扩展，均以本文档为准，冲突时本文档优先于旧文档中被扩展的条目。
>
> 后端实现范围：`Fleet`/`DriverFleet`/`VehicleFleet` 数据模型与迁移；`Driver.serviceOrganizationId` 改为可选；`master-data` 模块新增车队 CRUD 与成员管理接口（`/fleets`）、司机列表支持"无承运商"与按车队筛选；`waybill.service.ts` 支持 `SOCIAL` 模式与车队继承校验、新增 `PATCH /waybills/:id/carrier`（含移动端代理路由）；`logistics-settlement.service.ts` 候选列表新增 `carrierPending` 字段并在创建结算单时校验。
>
> 前端实现范围：物流管理下的"运力管理"（车辆/司机/车队三子页签，含车队成员管理面板）；运单创建、批量创建、详情、列表、调度看板页支持"社会运力"及开票承运商绑定；结算候选列表提示 `carrierPending`；移动端小程序同步支持三态 `freightMode`。

## 背景

实际业务中找车存在三种松散程度不同的来源：正式注册、能开票的物流公司；没有工商主体但长期一起接活的车队；完全独立的个体司机。只有第一种能直接开票，后两种需要"挂靠"某个物流公司才能完成开票，而挂靠对象往往在车辆已经发运之后才确定。现有设计把"车辆/司机是否属于某个承运商"和"运单运输方式"强绑定在建单那一刻，无法表达这种后置的挂靠关系，也无法表达司机脱离任何承运商独立存在、以及一群车辆/司机作为松散整体管理的需求。

## 一、数据模型

### 1.1 司机脱离承运商独立存在

`Driver.serviceOrganizationId` 由必填改为可选。司机档案不再要求先有物流承运商档案才能创建。

```text
Driver
  serviceOrganizationId  String?  （原为必填，改为可选）
```

没有 `serviceOrganizationId` 且不属于任何已绑定承运商的车队的司机，业务上只能用于 `Waybill.freightMode = SOCIAL`（见 1.3）。

司机采用“一人一档”规则：有效司机档案的手机号全平台唯一；身份证号、驾驶证号填写后也全平台唯一且忽略字母大小写。司机更换承运商或加入多个车队时，不重复创建司机档案，只调整承运商或车队关联。已被业务单据引用的司机不能删除，可停用并保留历史追溯。

### 1.2 新增 `Fleet`（车队）

车队是纯粹的分组管理单元，不是 `Partner` 体系的一部分，不能升级为正式合作伙伴/服务生态档案。

```text
Fleet
  id
  name              车队名称/队长名称
  contactPerson
  contactPhone
  carrierPartnerId  String?   挂靠的开票承运商，可随时改绑，可清空
  remark
  status             ACTIVE | INACTIVE

DriverFleet（多对多关联表）
  driverId
  fleetId

VehicleFleet（多对多关联表）
  vehicleId
  fleetId
```

一个司机/车辆可以同时加入多个车队；一个车队可以有多个司机和车辆。车队与车辆/司机都是独立维度，车队不改变车辆自身的 `ownerType`/`ownerId`，也不要求成员司机/车辆之间有任何其他共同属性。

### 1.3 `Waybill.freightMode` 新增 `SOCIAL`（社会运力）

```text
freightMode: SELF | THIRD_PARTY | SOCIAL
```

三种模式在建单时的差异：

| 模式 | 车辆/司机校验 | 建单时是否要求 `carrierPartnerId` |
|---|---|---|
| `SELF` | 车辆 `ownerType` 必须是 `SELF`；司机所属承运商必须是内部企业 | 否，不适用 |
| `THIRD_PARTY` | 车辆 `ownerId`、司机 `serviceOrganizationId`（或所在车队的 `carrierPartnerId`）必须与所选承运商一致 | 是，发运前必填 |
| `SOCIAL` | 不校验车辆/司机归属，可选已有档案（下拉）或纯文本手工填写 | 否，可留空，后续通过独立接口补绑 |

`SOCIAL` 模式下，车辆/司机即使选择了已有主数据档案，也不检查其 `ownerId`/`serviceOrganizationId`——这正是"挂靠"场景的本质：车和人并非真实归属于最终开票的公司。

### 1.4 承运商资质解析增加车队继承

`resolveCarrier` 系列校验判断"司机/车辆是否归属某承运商"时，增加车队继承的"或"条件：

- 司机：`driver.serviceOrganizationId` 对应的 Partner 等于所选承运商，**或** 司机所在任一 `DriverFleet` 关联车队的 `carrierPartnerId` 等于所选承运商
- 车辆：`vehicle.ownerId` 等于所选承运商，**或** 车辆所在任一 `VehicleFleet` 关联车队的 `carrierPartnerId` 等于所选承运商

车队一旦绑定承运商，队内全部司机和车辆立即可以在 `THIRD_PARTY` 模式下直接使用，不需要逐个单独挂靠。车队解绑或改绑承运商后，此前依赖该车队关系建立的 `THIRD_PARTY` 运单不受影响（运单保存的是建单时刻的快照 `carrierPartnerId`/`carrierName`，不随车队后续改绑联动变化）。

## 二、运单层：开票承运商延迟绑定

### 2.1 新增接口

```text
PATCH /waybills/:id/carrier
  { carrierPartnerId: string }
```

- 仅适用于 `freightMode = SOCIAL` 的运单；`SELF`/`THIRD_PARTY` 运单的承运商变更走现有 `PATCH /waybills/:id/assignment`（仅 `PENDING` 状态可用）的既定流程，不复用本接口
- **不受运单状态限制**，`PENDING` 到 `SIGNED` 任一阶段均可调用，支持车辆已经发运、甚至已经签收之后再补绑
- 校验逻辑与 `resolveCarrier` 一致：所选 Partner 必须有状态 `ACTIVE` 的 `LOGISTICS_CARRIER` 服务生态档案，且该 Partner 具备 `SUPPLIER` 角色
- 只更新 `carrierPartnerId`/`carrierName` 两个字段，不触发、不校验车辆或司机的归属一致性
- 绑定后 `freightMode` 保持 `SOCIAL` 不变，不回写为 `THIRD_PARTY`——车辆司机的真实归属事实并未改变，只是开票对象确定了

### 2.2 结算候选环节把关，运单状态机本身不设强制卡点

[物流合同与结算模块](./物流合同与结算模块.md)的 `listCandidateWaybills` 当前只过滤 `status = SIGNED` 且未被有效结算单占用的运单，不检查 `carrierPartnerId` 是否为空。扩展为：

- 候选列表返回字段增加 `carrierPending: boolean`（即 `carrierPartnerId` 为空）
- 不从候选列表中物理剔除这些运单，前端对 `carrierPending = true` 的行禁用勾选，提示"请先确定该运单的开票承运商"
- 运单本身从 `PENDING` 到 `SIGNED` 全程不强制要求 `carrierPartnerId`；该字段的"必须补齐"时机由结算环节把关，不在运单状态机里设置任何超时或截止点

## 三、运力资源管理菜单

车辆、司机、车队是日常物流作业资源。菜单从高权限的主数据管理迁至**物流管理 → 运力管理**，原主数据入口移除；原详情链接暂保留，以免历史链接失效：

```text
主数据管理
  ├── 合作伙伴
  ├── 服务生态        （物流承运商/质检机构/仓储港口/加工服务商档案创建，不变）
  ├── 物料品类
  ├── 仓库库位
  ├── 价格基准
  └── 质检标准

物流管理
  └── 运力管理        （车辆 / 司机 / 车队）
```

物流承运商的创建维持在"服务生态"中，与质检机构、仓储港口、加工服务商并列，不迁移——"服务生态"管的是具备正式资质、可被选为交易对手的合作伙伴专业档案，"运力管理"管的是具体执行运输的人和车，两者是不同维度，对应关系见下表。

| 维度 | 归属 | 能否直接开票 |
|---|---|---|
| 服务生态 · 物流承运商 | `Partner` + `ServiceOrganization` | 能 |
| 运力管理 · 车队 | 独立 `Fleet`，可选绑定承运商 | 不能，挂靠后由所绑承运商开票 |
| 运力管理 · 车辆 / 司机 | 可选归属承运商、可选加入车队、也可完全独立 | 不能 |

司机列表页独立后，支持按"所属承运商"（含"无承运商"）和"所属车队"筛选；创建司机表单的承运商字段改为可选。

## 五、权限边界

- 司机、车辆、车队及其附件统一采用 `transport_resource.view` / `transport_resource.manage`；物流岗位可维护运力资源，不因此取得合作伙伴、组织、物料等 `master_data.manage` 权限。
- 迁移为已有物流查看/维护或主数据查看/维护角色补齐对应运力权限；外部企业的许可仍遵守外部账号白名单，不自动扩大范围。
- 运力页获取承运商下拉选项走 `/transport-resources/carriers` 的窄接口，不暴露完整合作伙伴与服务生态管理接口。
- `PATCH /waybills/:id/carrier` 归入 `logistics.manage`，与运单其他管理操作同权限
- 车队本身不是合作伙伴，不参与[权限与数据范围规范](../../产品/权限与数据范围规范.md)定义的外部企业数据范围继承链；外部企业账号不会因为车队挂靠关系而获得额外的可见运单范围

## 六、本次不做

- 不支持车队升级/转换为正式 `Partner` + `ServiceOrganization`；车队转为正式承运商需要在服务生态中重新建档，车辆/司机需要重新挂靠，旧车队记录归档保留，不做自动迁移
- 不区分"开票方"与"实际收款方"为两个独立字段，`carrierPartnerId` 同时承担两种语义（对应司机车队直接与物流公司结算、物流公司转付司机的模式；物流公司仅代开票收手续费、司机另行直接收款的模式本次不单独建模）
- 车队本身不承载价格/评级信息，不走审批或停用的常规主数据流程，仅有 `ACTIVE`/`INACTIVE` 两态
