# 主数据模块设计

> 版本：v1.0-draft | 日期：2026-07-03

## 整体思路

以 **合作伙伴 (Partner)** 为中心，将原来的 Supplier 表升级为统一的企业主体管理，通过合作伙伴角色区分供应商/客户。所有主数据实体遵循统一规范：编码唯一、软删除、状态管理。

---

## 一、合作伙伴 (Partner)

将原有的 `Supplier` 升级为 `Partner`，一个企业可同时具备多个合作伙伴角色。

### 合作伙伴编码规则

| 类型 | 位数 | 字符集 | 生成方式 | 示例 |
|------|------|--------|---------|------|
| **内部企业** | 6 位 | 字母+数字 | 手工录入，数据库唯一校验 | `100000`、`200001` |
| **外部企业** | 8 位 | 纯数字 | 系统自动生成（递增序列），可切换为手工输入 | `80000001`、`80000125` |

### Partner 表

| 字段 | 类型 | 说明 |
|------|------|------|
| id | String (cuid) | 主键 |
| code | String (unique) | 合作伙伴编码，编码规则见下方 |
| name | String | 企业全称「唯一校验：name + taxId」 |
| shortName | String? | 简称 |
| taxId | String? | 统一社会信用代码「唯一校验：name + taxId」 |
| legalPerson | String? | 法定代表人 |
| contactPerson | String? | 联系人 |
| contactPhone | String? | 联系电话 |
| address | String? | 注册地址 |
| bizAddress | String? | 经营地址 |
| sourceRegion | String? | 货源地（萤石产地：金华、武义、福建等） |
| creditLimit | Decimal? | 授信额度 |
| roles | String[] | 合作伙伴角色数组，多选：SUPPLIER / CUSTOMER |
| status | String | ACTIVE / INACTIVE / BLACKLIST |
| remark | String? | 备注 |
| createdAt/updatedAt/deletedAt | | |

> 合作伙伴角色是 Partner 的属性（字段），非独立关联表。创建时通过勾选多选确定合作伙伴角色。
> 唯一性校验：`@unique([taxId, name])`，统一社会信用代码 + 企业名称联合唯一。

### 合作伙伴角色类型说明

| 类型 | 说明 | 示例 |
|------|------|------|
| SUPPLIER | 外部供应商 | 萤石矿企、运输公司 |
| CUSTOMER | 外部客户 | 钢厂、氟化工企业 |
| CARRIER | 承运商 | 物流车队 |
| INTERNAL | 内部企业 | 集团子公司、分公司、内部业务部门 |

### 对 Contract 的影响

原有 Contract 的 `supplierId` 改为引用 `Partner`，新增 `buyerId` 也引用 `Partner`。这样一份合同可以做：
- 采购合同：Partner(供应商/SUPPLIER) → 我方内部企业(INTERNAL)
- 销售合同：我方内部企业(INTERNAL) → Partner(客户/CUSTOMER)
- 内部调拨：内部企业A(INTERNAL) → 内部企业B(INTERNAL)
- 双边合同：上下游都是 Partner

## 二、商品物料

物料采用“物料分类 → 平台标准商品 → 业务物料 → 库存/采购批次”四层模型。用户只操作一个简化建档表单，`StandardCommodity` 由后端自动查重和复用。

### MaterialCategory（物料分类）

| 字段 | 说明 |
|------|------|
| id | |
| name | 分类名称，如"萤石粉"、"萤石块矿" |
| parentId | 父级分类，支持二级分类 |
| sort | 排序 |

### StandardCommodity（平台标准商品）

| 字段 | 说明 |
|------|------|
| code | `STD` + 6 位流水号，全平台唯一 |
| name | `{品名}{形态}-{核心规格}` 自动拼接，包装不进入名称 |
| categoryId / baseName | 商品分类和基础品名 |
| commodityForm | 商品形态/品种 |
| coreSpecName / Operator / Value / Unit | 结构化核心规格 |
| packageType / unit | 包装方式和基本计量单位 |
| fingerprint | 上述稳定属性规范化后的唯一查重指纹 |

`fingerprint` 去除空白并忽略英文大小写，不包含参考类型。因此同一标准商品可以分别建立“贸易商品”和“产成品”业务物料，但两者复用同一平台标准身份。

### Material（业务物料）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | String | |
| code | String (unique) | 按参考类型生成：`TRD/RAW/SFG/FGD/AUX/PKG/SRV/OTH` + 6 位流水号 |
| name | String | 保存时复制的标准名称，供历史单据兼容 |
| categoryId | String | 关联 MaterialCategory |
| standardCommodityId | String? | 关联 StandardCommodity，历史数据迁移时自动补建 |
| referenceType | String | 参考类型，只用于编码、检索和统计，不参与流程限制 |
| commodityForm | String? | 商品形态快照 |
| grade | String | 品级/规格描述，如"CaF₂≥97%" |
| unit | String | 单位，默认为 TON |
| spec | String? | 规格参数，如"-200目" |
| sourceRegion | String? | 主要产地 |
| packageType | String? | 包装方式（散装/吨袋/小包装） |
| status | String | ACTIVE / INACTIVE |
| remark | String? | |

创建时先按指纹查找或创建 `StandardCommodity`，再检查 `standardCommodityId + referenceType + deletedAt IS NULL` 是否已存在。系统自动编码发生并发冲突时最多重试 3 次，不对用户返回数据库 500 错误。

结构化建档不再接受独立的品名语义：后端以 `categoryId` 对应的分类名称作为 `baseName`，与 `commodityForm` 及核心规格拼接 `Material.name`。即使调用方传入不同 `baseName`，也不得绕过分类命名规则。

示例数据：

| code | referenceType | standard name | unit |
|------|---------------|---------------|------|
| TRD000001 | TRADING_GOODS | 萤石精粉-CaF₂≥97% | 吨 |
| RAW000001 | RAW_MATERIAL | 萤石原矿-CaF₂≥57% | 吨 |
| FGD000001 | FINISHED_GOODS | 萤石精粉-CaF₂≥97% | 吨 |

## 三、车辆 (Vehicle) — 新建

大宗商品运输是重物流场景，车辆作为平台级主数据独立维护。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | String | |
| plateNo | String (unique) | 车牌号 |
| vehicleType | String | 车型：TRUCK（自卸车）/ TANK（罐车）/ TRAILER（挂车） |
| brand | String? | 品牌型号 |
| tareWeight | Decimal? | 整备质量/参考皮重 |
| loadCapacity | Decimal | 核定载重(吨) |
| plateColor | String? | YELLOW / GREEN / BLUE / BLACK / OTHER |
| licenseNo | String? | 行驶证号 |
| annualInspectionExpiry | DateTime? | 年检到期日 |
| compulsoryInsuranceExpiry | DateTime? | 交强险到期日 |
| commercialInsuranceExpiry | DateTime? | 商业险到期日 |
| ownerId | String? | 所属单位（关联 Partner）；自有车辆可关联内部主体，外协车辆必须关联物流承运商 |
| ownerType | String | SELF（自有）/ OUTSOURCED（外协） |
| ownerName / ownerPhone | String? | 实际车主及联系方式 |
| deviceType / deviceNo | String? | 北斗/GPS设备类型和终端号 |
| deviceInstalledAt | DateTime? | 设备安装日期 |
| status | String | ACTIVE / MAINTENANCE / RETIRED |
| remark | String? | |

车辆接口支持分页、搜索、归属/承运商/车型/状态筛选、新建、详情、修改和软删除。车牌写入前统一去空格、间隔符并转大写，数据库唯一索引和服务层重复校验共同保证全平台唯一。外协车辆创建时 `ownerId` 必填且必须对应有效物流承运商。只有无物流运单引用的车辆允许软删除；已使用车辆通过 `MAINTENANCE` 或 `RETIRED` 退出候选范围。

`VehicleDriver` 是车辆与司机的显式关联表，使用 `role=PRIMARY/SECONDARY` 区分主驾和副驾；同一车辆司机唯一且最多一名主驾。外协车辆只能关联所属承运商的司机，自有车辆只能关联内部物流服务商司机。`Vehicle.driverName/driverPhone` 仅保留为历史兼容和主驾快捷快照，新逻辑以关联表为准。

车辆列表的 `operationStatus` 不入库：存在有效 `IN_TRANSIT` 运单时为“在途”，否则为“空闲”。围栏、最后位置和轨迹不得从档案字段推断，必须由真实定位平台数据产生。

`Waybill.vehicleId` 保存车辆主数据引用，同时 `plateNo`、`driverName`、`driverPhone` 和 `carrierName` 保存调度时快照。待发运阶段允许重新调度；进入在途后锁定快照，车辆主数据的后续修改不回写历史单据。

### 司机（Driver）

司机是独立于车辆的可复用主数据，通过 `serviceOrganizationId` 归属类型为 `LOGISTICS_CARRIER` 的服务生态档案。核心字段包括姓名、手机号、身份证号、驾驶证号、准驾车型、驾驶证有效期和状态；同一物流承运商下手机号唯一。查询接口支持按司机、手机号、证件号和承运商名称模糊搜索。

`Waybill.driverId` 保存司机档案引用，`driverName`、`driverPhone` 继续保存本车次执行快照。第三方运输校验司机所属承运商与 `carrierPartnerId` 一致；自有运力仅允许引用内部物流服务商司机。历史运单引用存在时司机只能停用，不能删除。

## 六、设计决策记录

| 决策 | 选项 | 选择 | 理由 |
|------|------|------|------|
| 供应商/客户分表还是统一 | 分表 / 统一 Partner | **统一 Partner** | 一家企业可能同时是供应商和客户，统一管理避免数据冗余 |
| 物料分类用字段还是表 | 字段 / 分类表 | **分类表** | 大宗贸易物料分类层次清晰，分类表便于筛选和日后扩展 |
| 价格信息 | 单独表 | **暂缓，放在后续行情模块** | 价格数据量和分析需求超出现有范围，一期先保证基础 CRUD 可用 |

## 七、权限边界与待收口

- 主数据查看和管理目标权限为 `master_data.view` / `master_data.manage`。
- 合作伙伴、银行账户、物料、仓库和车辆属于平台基础档案，不能直接套用“外部企业合同关联数据”范围。
- 当前主数据接口的外部企业专属只读视图尚未完成；外部账号上线前需逐接口接入功能权限并定义可见字段，尤其保护银行账户、证照和联系人信息。
- 完成该项前，外部账号不得授予 `master_data.manage`，主数据维护由内部平台管理员执行。
- 业务单据中的主数据名称快照随所属单据范围访问，不因主数据接口暂未开放而影响业务追溯。

统一规则见[角色权限与数据范围](./角色权限与数据范围.md)。
