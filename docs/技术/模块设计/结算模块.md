# 资金结算模块设计

## 目标与边界

完成“合同/执行批次业务依据 → 应收或付款申请 → 收款认领/付款审批 → 资金确认 → 核销/撤销 → 结算台账”的采购、销售资金闭环。一级菜单为“资金结算”；侧边栏二级菜单为“应收管理”、“应付管理”和“结算台账”。应收管理页顶部切换“应收款计划”、“收款单”；应付管理页顶部切换“付款申请单”、“付款单”。完整业务层级由面包屑展示，不在侧边栏堆叠三级菜单。运费结算继续由物流结算模块负责；发票、银行流水自动导入匹配和会计凭证属于下一阶段。

## 前端信息架构

| 菜单 | 职责 | 是否维护源单据 |
|---|---|---|
| 应收管理 / 应收款计划 | 销售方向应收结算确认、核销和追踪 | 是 |
| 应收管理 / 收款单 | 实际收款、预收款及反向退款等资金流水 | 是 |
| 应付管理 / 付款申请单 | 业务准备、财务提交、三级审批及待付金额控制 | 是 |
| 应付管理 / 付款单 | 记录、查看并确认已经实际执行的付款流水 | 是 |
| 结算台账 | 按合同聚合结算、资金、核销、未结和逾期 | 否，只读汇总 |

旧地址 `/dashboard/settlement` 保留兼容跳转到 `/dashboard/receivables`，不再作为独立业务页面。

## 数据模型

| 模型 | 作用 | 关键字段 |
|---|---|---|
| `FinancialSettlement` | 应收/应付结算单头 | direction、settlementScope、contractId、businessUnitId、legalEntityPartnerId、totalAmount、settledAmount、status |
| `FinancialSettlementLine` | 执行批次结算快照 | settlementId、orderId、quantity、unitPrice、grossAmount、adjustmentAmount、totalAmount |
| `FundTransaction` | 实际资金流水、预收预付、保证金和退款 | businessType、direction、paymentStage、paymentMethod、amount、currency、paymentPurpose、实际双方账户、recognitionProvider、recognitionRawText、paymentRequestId |
| `PaymentRequest` | 实际付款前的申请与审批单 | contractId、settlementId、relatedTransactionId、amount、状态、计划账户快照、approvedBy、fundTransactions |
| `SettlementAllocation` | 核销与撤销痕迹 | settlementId、fundTransactionId、amount、reversedAt、reversalReason |

法律主体与业务单元分别保存：前者决定往来、收付款归属，后者决定经营责任与利润统计。

## 状态机

```text
结算单：DRAFT → CONFIRMED → PARTIALLY_SETTLED → SETTLED
             └──────────────────────────────→ VOIDED（仅未核销）

收款流水：PENDING_CLAIM → PENDING_CONFIRMATION → CONFIRMED → PARTIALLY_ALLOCATED → ALLOCATED
付款流水：PENDING_CONFIRMATION → CONFIRMED → PARTIALLY_ALLOCATED → ALLOCATED
付款申请：DRAFT → BUSINESS_CONFIRMED → PENDING_APPROVAL → APPROVED → PARTIALLY_PAID → PAID

收款单：PENDING_CLAIM → PARTIALLY_CLAIMED → PENDING_CONFIRMATION → CONFIRMED → PARTIALLY_ALLOCATED / ALLOCATED
                 └→ REJECTED          └→ VOIDED（付款前）

核销记录：有效 → REVERSED（记录撤销人、时间和原因，不物理删除）
```

## 正式结算单打印

- 结算详情对 `CONFIRMED`、`PARTIALLY_SETTLED`、`SETTLED` 三种有效状态开放“打印存档”；`DRAFT` 和 `VOIDED` 在前后端均禁止打印。
- 打印使用独立路由 `/dashboard/settlements/:id/print`，屏幕上保留返回和打印操作区，打印介质中隐藏运营后台侧边栏、页头和操作按钮，按 A4 纵向排版。
- 结算单使用真实业务快照，包含合同与结算编号、结算口径、执行批次明细、加减项、大小写金额、有效核销记录、制单/确认信息及双方签章区；不在打印层重新计算业务结果。
- 供应方和采购方由结算方向确定：应付为“交易对手方 → 供应方、我方主体 → 采购方”，应收相反。地址、联系人和默认有效银行账户来自合作伙伴主数据。
- 用户点击打印时先调用打印接口，统一业务操作拦截器写入 `FINANCIAL_SETTLEMENT / PRINT / 打印存档` 审计记录，再调起浏览器打印面板。接口只记录打印发起，不声明纸质文件已经完成签章或入档。

## 付款申请审批流程

- 付款申请复用 `ApprovalFlow` / `ApprovalFlowNode` 配置表，以历史兼容字段 `contractType = PAYMENT_REQUEST` 标识业务类型，并在「系统管理 → 审批流程」与三类合同流程统一维护。
- 审批任务使用独立的 `PaymentRequestApproval` 表，按付款申请、轮次、节点和审批人记录 `WAITING / PENDING / APPROVED / REJECTED / OTHERS_APPROVED / OTHERS_REJECTED / CANCELLED`，不复用合同审批任务，避免同一合同多张付款申请串单。
- 申请提交时按节点角色、角色有效期、人员范围和付款申请所属业务单元解析成员并形成快照；业务单元归属仍是内部普通账号的最高数据边界。管理员提交且节点无人时可使用管理员兜底，普通用户不得绕过缺失配置。
- 付款申请由采销业务员或运营经理创建和业务确认，状态进入 `BUSINESS_CONFIRMED`；具备 `settlement.payment.submit` 的财务岗位复核后正式提交审批。默认流程为“风控/财务经理 → 业务责任人 → 总经理”，采用或签；业务责任人节点按付款申请所属业务单元解析。全部启用节点通过后付款申请才进入 `APPROVED`，出纳随后“创建付款单”。驳回、作废会取消仍处于等待或待处理状态的任务，重新提交产生新一轮审批记录。
- 已批准或已创建付款单的付款申请开放独立 A4 打印页，打印前调用专用接口写入 `PAYMENT_REQUEST / PRINT / 打印存档` 操作记录；其他状态由前后端共同禁止打印。
- 结算单、付款申请和资金单据使用独立详情路由，完整展示关联关系、附件、审批/核销轨迹和管理员操作记录。付款单创建使用 `/dashboard/payments/create` 独立页面，承载付款申请选择、凭证预览、OCR 回填和账户核验，不再使用付款申请页内弹窗。
- 迁移上线时，旧版本没有审批任务的 `PENDING_APPROVAL` 申请退回草稿，由原申请人重新提交以生成可追溯审批链。

## 日期与附件交互

- 日期、月份、时间和日期时间统一使用 `TemporalInput`。日期弹层通过显式点击或键盘操作打开，避免业务弹窗自动聚焦第一个日期字段时误弹；弹层在 Radix 模态框外层 Portal 中仍允许点击，并由面板内确认按钮写回表单。
- 付款申请与资金流水附件变更后重新请求当前单据详情，仅刷新附件和列表数据，不再把详情弹窗置空；支持连续上传、删除、预览以及后续业务操作。

## 核心校验

- 采购合同只能形成应付，销售合同只能形成应收；双边合同可分别形成两个方向。
- 收款允许出纳先按我方到账主体、账户和银行流水登记，不强制立即关联合同；业务人员通过 `FundClaim` 将一笔到账分笔认领到多个销售合同/执行批次，全部认领完成后才能财务确认。采购付款、客户退款及退还客户保证金必须从已审批付款申请执行，不能直接登记成已付款。
- 合同交易双方由合同锁定；银行流水实际付款方、收款方单独固化。第三方代付或代收必须显式标记并填写原因。
- 财务确认前必须上传银行回单或其他资金凭证；付款申请附件与银行回单均支持当前页面预览。
- 付款申请与付款单是一对多关系。一张已审批申请可分次付款，服务端按未作废付款单累计金额计算剩余待付并禁止超额；部分形成付款单时状态为 `PARTIALLY_PAID`，全部形成时为 `PAID`，付款单作废后重新计算申请状态。
- OCR 仅填充回单编号、付款/收款户名、账号、开户行、金额、币种、实际付款时间和用途。创建时必须携带原始凭证，保存 OCR 提供方及原始识别文本用于审计；未配置 OCR 或识别失败时允许人工填写，但不允许缺少原始凭证。
- 银行账号比较前移除空格、短横线等格式字符。实际账号与申请快照不一致时必须填写差异说明；匹配同一合作伙伴下其他有效账户可继续，匹配到其他企业已维护账户则阻止创建。计划账户快照与实际账户分别保存。
- 资金收付方向由业务类型和款项类型在服务端推导：采购通常付款、销售通常收款，退款与退回自动反向。
- 合同必须具备我方签约主体、交易对手和业务单元。
- 执行批次结算允许选择同合同、同采购/销售方向的草稿、已确认、执行中和已完成批次，以覆盖预付、发货后付、到货后付及尾款等场景；已取消和软删除批次不可选择。
- 批次未完成不构成接口硬拦截，系统展示批次状态并校验数量和金额不得超过批次剩余可结算值；付款合理性由付款申请审批承担。
- 结算详情通过结算明细的 `orderId` 实时读取批次状态并链接执行批次详情；付款申请详情链接关联结算单，使审批人能够核验当前履约阶段，结算明细金额仍保存创建时的业务快照。
- 合同阶段及最终结算受合同累计已结金额限制；最终结算金额由系统计算。
- 结算金额统一按“原金额＋加减项金额”计算；加减项非零时必须填写原因，正数增加、负数扣减。
- 草稿不计入正式应收应付、未结及逾期统计；到期日当天不算逾期，从次日开始计算。
- 结算单和资金流水继承合同权限范围，不按创建人单独放行。
- 核销双方必须具有一致的合同、收付方向、法律主体和交易对手。
- 核销金额同时受结算未结金额与资金可用余额限制。
- 保证金、退款与保证金退回不得参与货款核销；客户退款申请必须关联原收款单，申请中金额与已退款金额之和不得超过原流水未核销余额。
- 已核销单据不得直接作废；错误核销通过可审计的撤销操作纠正。
