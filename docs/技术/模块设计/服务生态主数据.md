# 服务生态主数据设计

## 数据模型

`ServiceOrganization` 是 `Partner` 的专业扩展档案，不是独立法人主体。通过 `partnerId + organizationType` 保证同一合作伙伴在同一专业类型下只有一条档案。

组织类型：

- `LOGISTICS_CARRIER`：物流承运商
- `QUALITY_INSTITUTION`：质检机构
- `WAREHOUSE_PORT`：仓储与港口服务商
- `PROCESSING_PROVIDER`：加工服务商

外部服务机构必须关联有效且 `roles` 包含 `SUPPLIER` 的合作伙伴。

## 业务关联

| 业务对象 | 关联字段 | 快照字段 | 说明 |
|---|---|---|---|
| 物流运单 | `carrierPartnerId` | `carrierName` | 第三方承运必须选择有效物流承运商 |
| 质检单 | `institutionPartnerId` | `institutionName` | 合作方、第三方检测必须选择有效质检机构 |
| 仓库 | `partnerId` | 仓库自身名称 | 租赁仓库必须选择有效仓储与港口服务商 |
| 生产任务 | `processorOrganizationId` | 通过关联档案读取合作伙伴名称 | 委外加工必须选择有效加工服务商 |

交易单据直接保存 `Partner.id`，专业档案用于准入、筛选和资质校验。名称快照用于保证合作伙伴更名后历史单据仍显示业务发生时名称。

## API

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/service-organizations` | 按类型、状态、关键词查询 |
| `POST` | `/service-organizations` | 创建服务生态档案 |
| `GET` | `/service-organizations/:id` | 查询详情 |
| `PATCH` | `/service-organizations/:id` | 更新资质、能力和状态 |

列表接口支持 `type`、`status`、`search`、`page`、`pageSize` 参数。

## 兼容策略

原有 `Waybill.carrierName` 和 `QualityInspection.institutionName` 保留为快照字段，新关联字段允许为空以兼容历史数据。新建第三方运单以及合作方、第三方质检单时必须选择预维护主数据。

## 权限边界

- 服务生态维护属于 `master_data.manage`，一期由内部平台账号维护。
- `ServiceOrganization` 身份用于业务准入和筛选，不自动成为单据访问参与方。
- 当前外部企业范围仍以合同卖方、买方或签约主体为根；承运商、质检机构和仓储服务商门户属于后续参与方映射设计。
- 服务商门户开放时需单独定义可见运单/质检/仓储记录及价格、合同金额等敏感字段，不能直接放开整条合同链。

统一规则见[角色权限与数据范围](./角色权限与数据范围.md)。

## 司机与车辆登记

后台建档统一从上司机、下车辆的页面进入，但两套主数据和主/副驾关联仍独立。承运商下“新增司机”复用该入口并带入当前服务组织；承运商不是必填项，社会运力允许暂不绑定。新增附件分别关联`Driver`或`Vehicle`，依照主数据权限访问，不从物流合同或运单继承附件权限。

见[司机与车辆统一建档](../../产品/司机与车辆统一建档.md)、[本轮开发备注](../开发备注/2026-10-22_司机车辆统一建档.md)。
