# 执行通知与物流模块设计

## 数据关系

```text
Order（合同执行批次）
  1:N DispatchNotice
      1:N DispatchNoticeLineItem
      1:N Waybill
          1:N WaybillLineItem
          1:N WeighTicket（发货/收货两个节点均可多张）
          1:N WaybillWeightSelection（同一次库存与结算执行磅单选用生成技术镜像）
```

`DispatchNotice` 通过 `orderId` 关联执行批次；通知明细通过 `orderLineItemId` 控制累计通知数量。`Waybill` 通过 `dispatchNoticeId` 关联执行通知；运单明细通过 `dispatchNoticeLineItemId` 控制累计运输数量。

批量派车不增加新的业务单据层级，仍采用“一辆车/一个运输趟次 = 一张 `Waybill`”。`Waybill.creationBatchId` 与 `creationRowId` 仅用于批量请求防重和技术追溯，不等同于合同执行批次，也不改变下游过磅、质检和出入库的一车一单关系。

`Attachment.waybillId` 关联物流运单，底层凭证分类保持 `RECEIPT_DOCUMENT`、`RECEIPT_PHOTO` 和 `RECEIPT_OTHER`。界面按业务方向显示为采购收货凭证或销售交付凭证。运单从 `ARRIVED` 进入 `SIGNED` 前，三类凭证合计必须至少存在一份，交接完成后凭证不可删除。历史 `RECEIPT` 数据继续兼容读取。

`Order.name` 是用户填写的业务识别名称，`Order.orderNo` 是系统生成的唯一编号。下游执行通知和物流运单选择器优先展示名称，同时保留编号与合同号，搜索同时覆盖名称和编号。

## 关键状态

- 执行通知：`DRAFT → ISSUED → IN_PROGRESS → COMPLETED`，草稿或未产生有效运单的已下达通知可以取消。
- 物流运单：`PENDING → IN_TRANSIT → ARRIVED → SIGNED`，待发运可以取消。
- 运单进入 `IN_TRANSIT` 时，执行通知由 `ISSUED` 推进为 `IN_PROGRESS`。
- 执行通知下达时，已确认执行批次进入执行中。

## 业务约束

- 一个执行批次可以拆分多张执行通知，一个执行通知可以拆分多张物流运单。
- 批量派车单次最多 100 行，允许同一通知使用多家承运商、临时车辆及同车多趟；每行必须具有车牌、司机、联系电话和至少一条正数物料数量。
- 批量接口首先按所有车辆汇总各通知明细数量，再在可串行化事务中锁定执行通知、重新计算有效运单占用量并统一创建，防止并发操作超出通知剩余数量。
- 单车和批量建单共用数据库级编号锁，连续分配 `WB-年月日-流水号`，避免并发生成重复编号。
- `batchRequestId + clientRowId` 构成幂等关系；同一请求重试返回原运单，不重复创建。批量创建动作分别写入各运单的操作记录。
- 车辆核定载重不足、同车同时间重复属于风险提示；通知数量越界、车辆/司机/承运商关系错误、计划时间倒置属于阻断校验。
- 非取消单据的累计数量不得超过上游单据数量。
- 执行通知的 `originLocation`、`destinationLocation` 均为必填地点快照，但不强制地点来源必须是仓库。采购、销售均可选择有效仓库、合作伙伴地址或直接填写，并允许带入后手工修正。
- 采购选择目的仓或销售选择起运仓时，同时写入库存操作 `warehouseId`；未选择仓库不阻止通知创建和下达，系统生成待补充仓库的现场作业单，实际入库或库存出库前再校验仓库。
- 运单确认发运前必须具备车牌和司机信息。
- 物流运单可引用状态为 `ACTIVE` 的车辆主数据并自动带入车牌、默认司机和手机号。`SELF` 仅可引用自有车辆；`THIRD_PARTY` 仅可引用所属单位与当前物流承运商一致的外协车辆。未建档的临时车辆仍允许手工录入，但不反向自动创建主数据。
- 物流运单可通过 `driverId` 引用启用司机档案并带入姓名、手机号，同时保留 `driverName`、`driverPhone` 快照。司机候选支持模糊搜索；第三方承运按当前承运商过滤，自有运力按内部物流服务商过滤，临时司机仍可手工录入。
- 运单选择车辆后从 `VehicleDriver` 读取主驾并默认选中，车辆关联的主/副驾在候选列表中优先排序；调度人员仍可选择同承运商其他司机，最终以运单 `driverId` 和快照为准。
- 第三方承运运单创建及调度时必须从主数据选择有效物流承运商；运单保存 `carrierPartnerId` 并保留 `carrierName` 名称快照。
- 预计到达时间必须晚于计划发运时间。
- 已发运后保留车牌、司机、承运单位等运输快照，不允许重新调度。
- 运单创建页提供本地规则文字识别，支持从非结构化调度文字中提取通知/批次/合同标识、车辆司机、承运信息、数量、地点和计划时间。识别结果只回填，不自动提交。
- 批量派车页支持每车一行的调度文本解析。单物料通知可以同时回填本车数量，多物料通知只自动建立车辆行，物料分配继续由用户逐项确认。
- 发货称重在运单有效期间均可补录；收货称重必须在运单到达或送达后录入。同节点追加完整磅单必须填写原因；从全部已复核磅单中统一选择一张库存与结算执行磅单，采购页面显示为结算入库磅单，销售页面显示为结算出库磅单。
- `DispatchNotice.qualityRequired` 决定目的地交接时是否自动生成质检任务；采购新建默认为真，销售新建默认为假。

## 调度工作台口径

- `PENDING` 且缺少车牌或司机：待调度。
- `PENDING` 且车牌、司机完整：待发运。
- `IN_TRANSIT`：在途；超过 `plannedArrivalAt` 时标记超时。
- `ARRIVED`：采购界面显示“已到达待收货”，销售界面显示“已送达待客户签收”。
- `SIGNED`：采购界面显示“已收货”，销售界面显示“客户已签收”，表示运输交接闭环完成。
- `CANCELLED` 不进入有效运单看板统计。

计划发运超时以 `plannedDepartureAt` 为判断依据，在途超时以 `plannedArrivalAt` 为判断依据。当前运输进度根据运单状态及 `departedAt`、`arrivedAt`、`signedAt` 三个实际节点时间生成。

程序内部继续使用 `Order` 表示合同执行批次，以兼容现有数据和接口。

## 权限与数据范围

- 执行通知使用 `execution.view` / `execution.manage`。
- 物流运单使用 `logistics.view` / `logistics.manage`。
- `DispatchNotice` 通过 `order.contract` 继承合同范围；`Waybill` 通过 `dispatchNotice.order.contract` 继续继承。
- 候选执行批次/通知、列表、详情、调度、状态流转和删除均在服务端合并范围条件。
- 运单附件通过所属运单关系执行相同范围；取得对象存储临时地址前必须先通过业务范围校验。
- 外部企业范围来自合同卖方、买方或签约主体，不按通知/运单创建人过滤。

统一实现见[角色权限与数据范围](./角色权限与数据范围.md)。

## 批量建单 API

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/waybills/batch` | 对一条已下达/执行中的执行通知批量创建 1—100 张独立物流运单 |

请求包含请求级 `batchRequestId`、执行通知 ID，以及带 `clientRowId` 的车辆行数组。返回创建数量、调度风险提示及全部运单。根运单创建在同一数据库事务中完成；过磅任务和销售车次出库作业在提交后按运单幂等补齐，网络重试时会继续补齐而不会重复建单。
