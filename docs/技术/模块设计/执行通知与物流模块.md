# 执行通知与物流模块设计

## 数据关系

```text
Order（合同执行批次）
  1:N DispatchNotice
      1:N DispatchNoticeLineItem
      1:N Waybill
          1:N WaybillLineItem
          1:N WeighTicket（同一时刻仅允许一张非作废磅单）
```

`DispatchNotice` 通过 `orderId` 关联执行批次；通知明细通过 `orderLineItemId` 控制累计通知数量。`Waybill` 通过 `dispatchNoticeId` 关联执行通知；运单明细通过 `dispatchNoticeLineItemId` 控制累计运输数量。

`Attachment.waybillId` 关联物流运单，物流收货凭证类别固定为 `RECEIPT`。运单从 `ARRIVED` 进入 `SIGNED` 前必须至少存在一份收货凭证，签收后凭证不可删除。

`Order.name` 是用户填写的业务识别名称，`Order.orderNo` 是系统生成的唯一编号。下游执行通知和物流运单选择器优先展示名称，同时保留编号与合同号，搜索同时覆盖名称和编号。

## 关键状态

- 执行通知：`DRAFT → ISSUED → IN_PROGRESS → COMPLETED`，草稿或未产生有效运单的已下达通知可以取消。
- 物流运单：`PENDING → IN_TRANSIT → ARRIVED → SIGNED`，待发运可以取消。
- 运单进入 `IN_TRANSIT` 时，执行通知由 `ISSUED` 推进为 `IN_PROGRESS`。
- 执行通知下达时，已确认执行批次进入执行中。

## 业务约束

- 一个执行批次可以拆分多张执行通知，一个执行通知可以拆分多张物流运单。
- 非取消单据的累计数量不得超过上游单据数量。
- 销售常规出库必须选择有效仓库，直拨模式允许不选择仓库。
- 运单确认发运前必须具备车牌和司机信息。
- 第三方承运运单创建及调度时必须从主数据选择有效物流承运商；运单保存 `carrierPartnerId` 并保留 `carrierName` 名称快照。
- 预计到达时间必须晚于计划发运时间。
- 已发运后保留车牌、司机、承运单位等运输快照，不允许重新调度。
- 运单创建页提供本地规则文字识别，支持从非结构化调度文字中提取通知/批次/合同标识、车辆司机、承运信息、数量、地点和计划时间。识别结果只回填，不自动提交。

## 调度工作台口径

- `PENDING` 且缺少车牌或司机：待调度。
- `PENDING` 且车牌、司机完整：待发运。
- `IN_TRANSIT`：在途；超过 `plannedArrivalAt` 时标记超时。
- `ARRIVED`：已到达，等待签收。
- `SIGNED`：已签收，运输闭环完成。
- `CANCELLED` 不进入有效运单看板统计。

计划发运超时以 `plannedDepartureAt` 为判断依据，在途超时以 `plannedArrivalAt` 为判断依据。当前运输进度根据运单状态及 `departedAt`、`arrivedAt`、`signedAt` 三个实际节点时间生成。

程序内部继续使用 `Order` 表示合同执行批次，以兼容现有数据和接口。
