# 入库与库存模块设计

## 1. 业务边界

本模块实现采购到货链路的第一版库存形成：

```text
采购物流运单
  → 已复核磅单
  → 最终质量验收依据（已确认、非熔断质检单）
  → 物流入库单
  → 业务入库单
  → 库存批次 + 库存台账
```

同一磅单可以有多张独立质检单，但每张物流入库单必须明确选定其中一张作为最终验收依据，避免多机构检测结果自动混用。

## 2. 数据模型

| 模型 | 职责 | 关键唯一约束 |
|------|------|--------------|
| `InboundReceipt` | 物流现场收货和验收依据快照 | `receiptNo` |
| `BusinessInbound` | 确认货权形成的业务入库凭证 | `inboundNo`、`receiptId` |
| `InventoryLot` | 按来源形成的库存批次 | `lotNo`、`businessInboundId` |
| `InventoryLedger` | 逐笔库存数量变动台账 | — |
| `Attachment` | 物流入库现场凭证 | `inboundReceiptId` 外键 |

首版一张采购物流运单只能存在一张未作废物流入库单。物流入库单保存物料、供应商、车牌、扣水扣杂、扣款和最终数量快照，防止上游数据后续变化影响已确认业务。

## 3. API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/inbound-receipts/eligible-waybills` | 查询可创建入库单的采购到货运单 |
| POST | `/inbound-receipts` | 创建物流入库单 |
| GET | `/inbound-receipts` | 关键词、状态查询 |
| GET | `/inbound-receipts/:id` | 查看完整详情 |
| PATCH | `/inbound-receipts/:id/confirm` | 确认收货 |
| PATCH | `/inbound-receipts/:id/cancel` | 作废草稿 |
| POST | `/inbound-receipts/:id/post` | 原子生成业务入库、库存批次、库存台账 |
| POST | `/inbound-receipts/:id/attachments` | 上传草稿收货附件 |
| DELETE | `/inbound-receipts/attachments/:id` | 删除草稿收货附件 |
| GET | `/inbound-receipts/attachments/:id/view-url` | 获取附件临时查看地址 |
| GET | `/inventory/overview` | 库存批次和汇总 |
| GET | `/inventory/ledger` | 库存台账 |

## 4. 一致性与校验

- 创建时服务端重新校验运单方向、运输状态、磅单状态、质检状态/结论和仓库状态。
- `FUSE`、未确认质检和未复核磅单不能绕过前端直接入库。
- 业务入库、库存批次、库存台账和物流入库状态更新在同一数据库事务中完成。
- `BusinessInbound.receiptId` 唯一，保证重复请求不会为同一物流入库单形成多份库存。
- 附件只在草稿状态可增删；确认后锁定为业务证据。
