# 入库与库存模块设计

## 1. 业务边界

本模块实现采购到货链路的第一版库存形成：

```text
采购物流运单确认发运
  → 自动生成待到货入库作业单
  → 到达/签收 → 过磅/复核 → 多机构质检
  → 指定最终质量验收依据（已确认且合格的质检单）
  → 现场收货确认
  → 业务入库单
  → 库存批次 + 库存台账
```

同一磅单可以有多张独立质检单。入库作业的有效磅单与最终质量验收质检单按运单归组、分别选择，不再要求质检单必须挂在有效入库磅单自身：有效磅单提供净重基数，最终合格质检单提供扣水、扣杂和质量结论，最终入库量为“有效磅单净重 − 扣水 − 扣杂”。第一张进入 `CONFIRMED + PASS` 的质检单自动补齐既有作业单，待入库阶段可以人工切换到同运单下其他合格单。

## 2. 数据模型

| 模型 | 职责 | 关键唯一约束 |
|------|------|--------------|
| `InboundReceipt` | 采购在途开始的入库作业任务、全过程节点汇总、物流现场收货和最终验收依据快照 | `receiptNo` |
| `BusinessInbound` | 确认货权形成的业务入库凭证，保存采购合同我方签约主体 `ownerPartnerId` | `inboundNo`、`receiptId` |
| `InventoryLot` | 按来源形成的库存批次，独立保存库存主体和物理仓库 | `lotNo`、`businessInboundId` |
| `InventoryLedger` | 逐笔库存数量变动台账 | — |
| `Attachment` | 物流入库现场凭证 | `inboundReceiptId` 外键 |

一张采购物流运单只能存在一张未作废入库作业单。作业单创建初期保存计划数量、物料、供应商、车牌和目标仓库；`weighTicketId`、`qualityInspectionId`、`acceptanceConclusion`、`receivedQuantity` 允许为空，由后续作业逐步补齐。最终验收确定后保存扣水扣杂、扣款和最终数量快照，防止上游数据后续变化影响已确认业务。

作业阶段不重复存储一套易失真的状态字段，而是根据来源单据实时派生：运单状态、有效磅单及复核状态、同车质检单及结论、入库单收货/入账状态共同计算 `workflow.stage`、节点完成情况和当前阻塞提示。

## 3. API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/inbound-receipts/eligible-waybills` | 查询可创建入库单的采购到货运单 |
| POST | `/inbound-receipts` | 手工补录物流入库单（兼容接口，主流程不使用） |
| GET | `/inbound-receipts` | 关键词、状态查询 |
| GET | `/inbound-receipts/:id` | 查看完整详情 |
| PATCH | `/inbound-receipts/:id` | 补充待入库单仓库、实际收货时间、收货人和备注 |
| PATCH | `/inbound-receipts/:id/acceptance-quality` | 选择同运单下已确认合格质检单作为最终验收依据 |
| PATCH | `/inbound-receipts/:id/confirm` | 确认收货 |
| PATCH | `/inbound-receipts/:id/cancel` | 作废待入库单 |
| POST | `/inbound-receipts/:id/post` | 原子生成业务入库、库存批次、库存台账 |
| POST | `/inbound-receipts/:id/attachments` | 上传待入库收货附件 |
| DELETE | `/inbound-receipts/attachments/:id` | 删除待入库收货附件 |
| GET | `/inbound-receipts/attachments/:id/view-url` | 获取附件临时查看地址 |
| GET | `/inventory/overview` | 总库存、仓库汇总、主体汇总、主体×仓库汇总和库存批次；支持主体、仓库和关键词过滤 |
| GET | `/inventory/ledger` | 库存台账 |

## 4. 一致性与校验

- 采购运单从 `PENDING` 进入 `IN_TRANSIT` 时调用库存域服务自动创建 `PENDING` 入库作业单；进入 `ARRIVED` 时再次幂等调用作为漏单兜底。
- 升级迁移会为已有 `IN_TRANSIT`、`ARRIVED`、`SIGNED` 采购运单幂等回填缺失的入库作业单；升级后运单进入签收时也会再次执行兜底检查。
- 质检状态进入 `CONFIRMED + PASS` 时，库存域服务补齐既有作业单的磅单、最终验收质检、扣减金额和实际数量；仅在历史数据或异常漏单场景下兜底创建。
- 数据库使用按运单过滤的活动入库单唯一索引，应用层同时检查已有单并处理并发唯一冲突，保证重复点击或并发确认不会生成两张待入库单。
- 自动单允许磅单、质检单、最终数量、仓库、实际收货时间和收货人在早期作业阶段为空；确认收货前必须补齐最终验收、仓库、时间和收货人。
- 确认收货和正式入账时，服务端重新校验最终验收质检状态和结论，只有 `CONFIRMED + PASS` 可以继续；提前生成作业单本身绝不增加库存。
- 确认收货和入账时同时校验 `InboundReceipt.weighTicketId` 必须等于运单当前 `INVENTORY` 有效磅单；磅单更换会同步未入账作业单的重量快照，已入账后禁止更换。
- `DEDUCTION`、`FUSE`、`PENDING`、未确认质检和未复核磅单不能绕过前端直接入库；历史不合格待入库单同样被确认及入账接口拦截。
- 业务入库、库存批次、库存台账和物流入库状态更新在同一数据库事务中完成。
- 入账时从采购合同 `signingPartnerId` 固化 `BusinessInbound.ownerPartnerId` 和 `InventoryLot.ownerPartnerId`；缺少我方签约主体时禁止形成库存。
- 库存的核心维度为“库存主体 + 仓库 + 物料 + 批次”。总库存仅为用户可见批次的统计合计，不代表不同主体之间可以调剂。
- 在库总览按“全平台总量 → 各仓库合计 → 各主体合计 → 主体×仓库明细”展示。仓库合计可包含多个库存主体，明细核算仍保持主体隔离。
- 销售通知冻结和车次批次拣配同时校验销售合同我方签约主体，只能占用同主体、同仓库、同物料库存。
- `BusinessInbound.receiptId` 唯一，保证重复请求不会为同一物流入库单形成多份库存。
- 附件只在待入库状态可增删；确认后锁定为业务证据。

## 5. 后续扩展

- 让步接收审批：超标货物经有权人员审批后形成独立验收结论，未上线前 `DEDUCTION` 不得入库。
- 销售出库、库存预占和批次扣减。
- 库位、调拨、盘点、报损报溢。
- 入账冲销和反向台账。
- 批次成本与结算中心联动。

## 6. 权限与数据范围

- 入库、库存批次和台账查看使用 `inventory.view`；创建、确认、作废、入账和附件增删使用 `inventory.manage`。
- `InboundReceipt` 通过 `waybill` 继承合同范围。
- `BusinessInbound` 通过 `receipt`、`InventoryLot` 通过 `businessInbound`、`InventoryLedger` 通过 `lot` 连续继承。
- 库存总览先应用范围再计算主体数、批次数、物料数、仓库数和总数量，禁止向非全量账号返回平台全量汇总。
- 附件通过物流入库单关系校验相同范围。

统一实现见[角色权限与数据范围](./角色权限与数据范围.md)。
