# 物流合同与结算模块设计

> 当前口径：2026-10-22。覆盖2026-09-18初版及2026-10-12主体修正中与下文不一致的旧约定。产品说明见[物流合同与运费结算迭代方案](../../产品/物流合同与运费结算迭代方案.md)。

## 数据模型

- `LogisticsContract`：合同名称、外部合同号、`signingPartnerId`（内部合作伙伴法律主体）、承运方、日期、付款条件、默认重量依据、状态及终止时间。`companyId`仅为管理组织兼容字段，不用于决定法律签约或事业部归属。
- `allBusinessUnits=true`默认适用于全部事业部；为false时通过`LogisticsContractBusinessUnit`明确多选范围。
- `LogisticsContractPriceTerm`：路线、含税单价、有效期。空字符串路线表示不限路线，两端必须同时填或同时空。同合同同路线日期区间不允许重叠。
- `LogisticsSettlement`：`ownerPartnerId`保留原货主，`payerPartnerId`为本次付款主体，另保存事业部、承运方及付款主体变更原因。
- `LogisticsSettlementLine`：一车一行，保存物料、时间、两端净重、选用磅单、毛皮净重、计费数量与方式、原合同价、本次单价、金额、原因及凭据快照。
- `LogisticsSettlementAdjustment`：PRICE/WEIGHT/PAYER独立历史，每次追加，保留前后值、原因、操作人和时间。
- `Attachment`新增物流合同和物流结算归属，使用现有MinIO文件服务及内容签名类型校验；附件查看仍受父单权限控制。

迁移：`20261022120000_logistics_contract_execution`。增量加字段/表；历史合同有组织企业合作伙伴映射时回填签约主体，无法映射的不猜测。历史结算保留原价和数量，旧行计费数量以原净重回填，不追溯重算。

## 主体、事业部和数据权限

法律签约主体来自Partner，不从员工所属Company推断。合同适用范围与单据经营归属分开：合同可共享，一张新结算必须是同一货主、事业部、承运方。

`getLogisticsContractScope`按当前权限允许的事业部与适用范围匹配，不能绕过顶层用户归属；ALL合同只共享档案，不共享运单和财务记录。`getLogisticsSettlementScope`要求全部运单可见（some非空 + every），不再按任一行可见放开整单。合同结算记录再次检查该范围。

## 计量口径

1. 采购：`INVENTORY`与`SETTLEMENT`仍统一选用结算入库磅单；最终采购货款由`BusinessInbound.quantity`和该过账关联磅单提供，不另取SETTLEMENT最新值。未过账/已冲销来源不能直接形成最终货物应付，预付款和阶段款保持原流程。
2. 销售：`INVENTORY`只选我方SHIPPING磅单，`SETTLEMENT`可选客户RECEIVING或约定的我方磅单。改销售货款依据不修改出库。出库已POSTED/READY/VARIANCE_PENDING仍不能直接改库存依据。
3. 运费：单独保存物流结算行的磅单与数量快照。合同参考口径按合同的SHIPPING/RECEIVING优先；SETTLEMENT下采购参考过账关联/当前入库磅单、销售参考当前货款磅单。Web新建表单显式提交选定的`weighTicketId`，界面默认RECEIVING，缺少时回退SHIPPING；这不是对合同参考口径或历史快照的改写。不同于合同参考口径、CONFIRMED或保存后更换依据需原因；CONFIRMED提交前需依据附件。
4. 物流计费选择不写`WaybillWeightSelection`、库存数量或货款结算。

### 新建结算的两端净重交互

- `apps/web/src/lib/logistics-weight.ts`统一筛除非正数或无效净重，按接口的最新优先顺序返回发货、收货磅单及默认ID。若用户明确选用同节点旧磅单，列表展示该张磅单，避免净重与实际计费来源不一致。
- 列表分列显示发货净重、收货净重及磅单号，通过单选框切换；两侧均有效且不相等时，较低侧用`text-primary`及“较低”标识，相同或缺一侧不标记。较低提示不影响默认收货选择。
- 列表单选框和下方计费磅单下拉框共享选择状态，切换磅单恢复TICKET计费并清空手工确认重量；修改合同运价保留已选磅单。选择按车次合同后不继续使用CONFIRMED重量。
- 新建界面提交前与合同参考磅单比较，提示补充原因；后端仍按原规则检查本运单有效磅单、原因及版本。保存时记录实际选用磅单，不改库存/货款依据或历史结算。
- `logistics-weight.test.ts`使用Node测试覆盖两端高低、相等、单端、无效重量、旧磅单及不修改源数据。

## 运价与金额

- 草稿可编辑，启用需签约主体、合同名称、附件和运价。生效后不再编辑运价/原合同，只在结算调价。
- 默认按实际发货日匹配（历史缺失时签收日兼容）；校验主体、承运方、事业部、合同及条款有效期。
- 精确路线优先不限路线，多份同优先级合同需显式选择。代付不自动更换原货主的运价来源。
- NET_WEIGHT按选定重量；TRIP按1车次；历史GROSS_WEIGHT按所选磅单毛重兼容。新建UI只主动提供净重和车次。
- Decimal逐行金额保留2位再合计，重量3位；不使用浮点累计资金。
- 调价保留`contractUnitPrice`及条款ID，不更新合同价格。每次改价、改量、换付款主体均追加历史。
- 提交和复核前校验所选磅单版本；复核后锁定。付款依据签名覆盖付款主体、原货主、计费数量、磅单、合同条款及金额。

## API

|---|---|---|
| GET | /logistics-contracts/options | 有权维护的事业部、签约主体及承运方引用 |

| POST | /logistics-contracts/:id/price-terms | 草稿新增运价 |

## 资金衔接及并发

物流结算已接入LOGISTICS付款申请，不再列为“未来待对接”。物流付款使用已复核结算作依据，审批后创建付款单、财务确认、物流专用核销及撤销；不混入采购货款额度。已有有效付款申请或核销时阻止物流结算直接作废。

创建按运单ID顺序加事务锁，避免一车重复结算；编号生成串行；结算调整/提交/复核/作废使用单据锁，并保留历史。销售磅单分用途选择保留旧版本，不反向回写库存。

## 验证与边界

- Jest覆盖主体、适用范围、锁价、磅单切换、车次计算、金额及资金保护。
- `scripts/smoke-logistics-contract.ts`：本地真实DB，合同→启用→采购/销售运费→调价/更换主体→复核，全事务回滚。
- `scripts/smoke-quality-payment.ts`：采购预付款→商务扣款接收→真实入库过账→最终结算→付款核销，另回归物流付款，全事务回滚。
- 批量导入、复杂路线编码、招投标、代开票税费分账、合同电子签章及物流预付款不在本轮范围。
- 物流合同本轮保留人工启用，不新增通用合同审批类型；物流结算沿用提交/复核，付款申请继续走既有可配置审批流。
