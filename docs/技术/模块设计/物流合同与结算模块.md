# 物流合同与结算模块设计（方案讨论稿）

> 状态：方案讨论中，尚未开发，用于和物流同事对齐后再排入迭代计划。

## 背景与范围

[执行通知与物流模块](./执行通知与物流模块.md)已经覆盖了从执行通知到物流运单、磅单的运输执行全流程，但"运费怎么谈、怎么算、怎么结算给承运方"目前没有模型覆盖。

需要注意本方案与规划中的"结算模块"（Iteration 7，`结算模块.md` 待编写，对应 `docs/产品/使用指南/结算模块.md`）是两个不同的结算对象：

- 既有"结算模块"规划的是贸易合同买卖双方的**应收/应付**（货款结算）。
- 本方案讨论的"物流结算"结算对象是**承运方**（运费结算），属于采购/销售履约成本的一部分。

两者数据模型相互独立，本文档只覆盖运费口径的合同与结算，不涉及应收应付；两者的对接关系见文末说明。

来源沟通信息：物流价格提前谈好、按吨计价、价格可能会调整；部分物流公司是固定价格合同；运满满价格不固定；临时车辆价格可能浮动，均无长期合同。

## 承运方建模（复用现有主数据，不新增模型）

物流运单创建时已经要求"第三方承运运单创建及调度时必须从主数据选择有效物流承运商"（见执行通知与物流模块.md 第 46 行），即 `ServiceOrganization(organizationType=LOGISTICS_CARRIER)` 关联的 `Partner` 记录已经是承运方在系统里的唯一入口。本方案不新建"承运方"模型，只需要：

- 为"运满满"和"临时车辆/散户"各登记一条 `Partner` + `ServiceOrganization(LOGISTICS_CARRIER)` 主数据，作为这两类无长期合同承运方在结算侧的统一归集点（散户可用 `Partner.category = TEMP` 标记，运满满按 `NORMAL` 处理）。
- 已有的合同物流公司承运方档案不用改动，只是在其基础上挂合同和运价条款。

## 数据关系

```text
Partner + ServiceOrganization(LOGISTICS_CARRIER)
  1:N LogisticsContract（仅长期合同物流公司使用）
      1:N LogisticsContractPriceTerm（路线+单价，按生效期分段，不区分货物品类）

Waybill（status = SIGNED，已有执行物流运单）
  1:1 WaybillWeightSelection(purpose = SETTLEMENT)  — 已有的结算执行磅单选择
  0:1 LogisticsSettlementLine  — 本方案新增，一趟运输只能被结算一次

LogisticsSettlement（物流结算单）
  1:N LogisticsSettlementLine
```

物流结算单不是独立的手工台账，而是对一批"已签收（SIGNED）、尚未结算"的 `Waybill` 做批量结算登记：明细行的车牌、收货时间、路线、货物、毛重/净重直接取自 `Waybill` + `WeighTicket`（经 `WaybillWeightSelection(purpose=SETTLEMENT)` 选出的那张磅单），只新增"单价、金额、单价来源"这几个结算特有字段，避免和执行侧数据出现两套口径、需要人工重复誊抄一遍毛重净重。

## 数据模型

### LogisticsContract（物流合同）

| 字段 | 说明 |
|---|---|
| carrierPartnerId | 承运方，必须关联 `ServiceOrganization(LOGISTICS_CARRIER)` 状态为 `ACTIVE` 的 `Partner` |
| companyId | 我方签约主体 |
| status | `DRAFT` / `ACTIVE` / `EXPIRED` / `TERMINATED` |
| settlementBasis | 默认 `NET_WEIGHT`（按净重结算），预留 `GROSS_WEIGHT`/`TRIP` |
| signedAt / effectiveAt / expireAt | |

仅用于长期合同物流公司；运满满、临时车辆不建合同。

### LogisticsContractPriceTerm（运价条款）

| 字段 | 说明 |
|---|---|
| contractId | |
| originLocation / destinationLocation | 与 `Waybill` 的地点快照保持同一套自由文本口径，不强制关联仓库主数据 |
| unitPrice | 元/吨，含税 |
| effectiveAt / expiresAt | 生效期；同路线改价时新增一条记录、旧条款收口 `expiresAt`，不覆盖旧数据，保证历史结算可追溯到当时生效的价格 |

不设货物维度：合同本身即针对特定物流目标签订（承运方+路线已经隐含了运什么货），无需在价格条款上再按货物品类拆分。

写入校验：同一 `contractId + originLocation + destinationLocation` 不允许存在两条日期区间重叠的记录。

### LogisticsSettlement（结算单头）

| 字段 | 说明 |
|---|---|
| settlementNo | 系统编号 |
| payerCompanyId | 货主方/委托方（我方主体） |
| periodStart / periodEnd | 结算周期 |
| status | `DRAFT` / `SUBMITTED` / `REVIEWED` / `VOIDED` |
| preparedBy / reviewedBy / preparedAt / reviewedAt | 对应截图的"制表人/复核人/制表日期" |
| totalGrossWeight / totalNetWeight / totalAmount | 冗余汇总，明细变化时重新计算 |

### LogisticsSettlementLine（结算单明细，一车一行）

| 字段 | 说明 |
|---|---|
| settlementId | |
| waybillId | 唯一（未作废范围内），一张运单只能进入一张结算单一次 |
| netWeight | 快照自 `WaybillWeightSelection(purpose=SETTLEMENT)`，即便后续磅单重新选择也不回溯改变已结算金额 |
| unitPrice | |
| priceSource | `CONTRACT`（合同自动带出，默认锁定） / `MANUAL`（运满满/临时车辆手工录入） / `CONTRACT_OVERRIDDEN`（合同价被人工改动） |
| contractPriceTermId | `priceSource` 为 `CONTRACT` 或 `CONTRACT_OVERRIDDEN` 时记录来源条款，用于留痕合同价与实付价差异 |
| overrideReason | `priceSource = CONTRACT_OVERRIDDEN` 时必填 |
| amount | `netWeight × unitPrice`，只读派生字段 |

## 关键流程

1. **创建结算单**：选择货主方主体 + 结算周期（可选按路线/承运方筛选），系统列出周期内所有 `status = SIGNED` 且未被结算（无有效 `LogisticsSettlementLine`）的 `Waybill` 供勾选加入，替代手工誊抄车牌、收货时间、毛重净重。
2. **单价匹配**：按每张 `Waybill` 的 `carrierPartnerId` 查找是否存在生效的 `LogisticsContract`；若存在且按"路线+收货日期"能匹配到一条 `LogisticsContractPriceTerm`，自动带出单价（`priceSource = CONTRACT`，默认锁定只读）；否则 `priceSource = MANUAL`，单价留空待手工填写（运满满、临时车辆均走这条路径）。
3. **人工调价**：有覆盖权限的人可以对 `CONTRACT` 行发起"手动调价"，必须填写 `overrideReason`，`priceSource` 变为 `CONTRACT_OVERRIDDEN`；合同原单价通过 `contractPriceTermId` 关联记录保留，供财务审计对比差异。
4. **计算与复核**：逐行/合计金额实时计算，提交进入复核；复核通过后单据锁定，不可再新增/移除明细行或改单价，如需调整须整单作废重开，保证审计轨迹完整。
5. **作废重开**：`DRAFT`/`SUBMITTED`/`REVIEWED` 状态均可直接作废（含复核通过后需要调整的场景），只要拥有 `logistics.settlement.manage` 权限且数据范围覆盖该结算单即可操作，不需要走审批流程。作废后关联 `Waybill` 重新回到"未结算"池，可被后续结算单再次选取；原结算单保留作为历史记录，新数据只能通过新建结算单产生。

## 业务约束

- 一张 `Waybill` 只能存在于一张非作废状态的结算单中。
- 只有 `status = SIGNED` 的 `Waybill` 才能被选入结算单；未签收/已取消的运单不可结算。
- `MANUAL` 单价没有自动匹配来源，提交前必须非空且大于零。
- `CONTRACT` 价格条款的重叠校验在写入合同价格条款时完成，避免同一天存在两条生效价格造成匹配歧义。
- 价格条款不区分货物品类，一份合同对应一条路线只允许一条当前生效价格。
- 复核通过后的结算单明细不可编辑，调整只能整单作废重开，作废本身不需要审批。

## 权限与数据范围

- 建议新增权限点：`logistics.contract.manage` / `logistics.contract.view`（物流合同）、`logistics.settlement.manage` / `logistics.settlement.view`（物流结算单）；复核动作可复用现有审批体系，或单独设 `logistics.settlement.review`，取决于是否要走通用审批流。
- 数据范围延续 `Waybill → dispatchNotice.order.contract` 的继承口径：结算单只能选取当前账号范围内可见的 `Waybill`；结算单本身的范围以其明细中 `Waybill` 所属合同的业务单元/企业为准，存在跨业务单元明细时按并集处理，与现有 `getContractScope` 的多条件 `OR` 逻辑一致。
- 统一实现方式参考[角色权限与数据范围](./角色权限与数据范围.md)。

## 与既有"结算模块"（应收应付）的关系

Iteration 7 规划中的"结算模块"面向合同买卖双方的应收/应付，结算对象是贸易合同的甲乙方；本方案的"物流结算"结算对象是承运方，是采购/销售履约成本的一部分。两者数据模型独立，不共用同一张结算单；物流结算单确认后的 `totalAmount` 未来可以作为一笔"运费成本"明细挂到对应合同的应付口径下，这部分对接属于后续迭代范围，本文档不展开。

## 关键决策记录

- **运价条款不分货物品类**：合同本身已经是针对特定物流目标签订的，承运方+路线隐含了货物范围，价格条款只按路线维度生效，不再叠加 `materialId` 约束。
- **结算周期不设固定账期**：`periodStart`/`periodEnd` 保持自由日期区间选择，不强制自然月或半月。
- **作废重开不走审批**：任何有 `logistics.settlement.manage` 权限、数据范围覆盖该结算单的人可以直接作废，不需要审批流程。
