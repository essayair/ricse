# 角色权限与数据范围设计

## 权限计算口径

RICSE 将账号授权拆分为两部分：

- 角色权限：决定用户可以执行哪些操作；
- 数据范围：决定该角色可以在哪些组织或企业数据上执行操作。

用户可以同时拥有多个角色。数据范围配置在用户的角色授权关系上，而不是固定在角色模板上。

授权通过的必要条件为：

```text
账号有效
  AND 至少一个有效角色包含目标功能权限
  AND 目标单据命中该用户有效授权的数据范围
```

多个角色不能把一个角色的功能权限与另一个角色的数据范围交叉组合。范围计算必须限定为“包含本次目标权限的有效角色授权”，再合并这些授权的范围。目标接口形态应统一为 `authorize(userId, permissionCode, resource)` 或 `getContractScope(userId, permissionCode)`，避免先全局 `assertPermission`、再从所有角色计算范围造成权限范围放大。

## 数据模型

| 模型 | 作用 |
|---|---|
| `Role` | 角色模板，分系统、管理和业务角色 |
| `Permission` | `资源.操作` 格式的权限字典 |
| `RolePermission` | 角色包含的功能权限 |
| `UserRoleAssignment` | 用户获得某个角色及其数据范围 |
| `UserRoleScope` | 指定企业、部门或仓库等范围明细 |

现有 `User.role` 字段暂时保留为主角色展示兼容字段，所有鉴权只认当前有效的 `UserRoleAssignment`，不再使用旧字段兜底管理员权限。修改用户授权时仍同步更新主角色，便于旧页面展示。

新建后台账号必须一对一关联有效员工和有效企业。除独立的系统初始化管理员外，企业账号一旦失去员工关联即视为孤立账号，禁止登录和重新启用。内部企业非管理员账号必须选择至少一个业务单元，初始角色默认使用 `BUSINESS_UNIT` 范围并写入已选单元；外部企业账号固定使用 `COMPANY` 范围；`ADMIN` 使用 `ALL`。历史孤立账号、无授权账号及旧版默认 `ALL` 的非管理员账号，可在发布维护窗口执行 `pnpm --filter @ricse/api prisma:repair-user-access` 幂等修复；脚本会清除孤立账号登录状态并将其停用，只收紧 `assignedBy` 为空的旧默认授权，不覆盖管理员显式配置的授权。若孤立账号是系统仅存的有效管理员，脚本会中止，避免锁死系统。

## 预置角色与权限

系统预置 14 个标准角色和 24 个基础权限。管理员拥有全部权限；其他预置角色提供默认岗位模板，系统管理员可为用户组合多个角色并配置每项授权的数据范围。

### 标准角色清单

| 角色编码 | 名称 | 默认职责 | 主要管理权限 |
|---|---|---|---|
| `ADMIN` | 系统管理员 | 平台配置、授权和全部业务兜底 | 全部权限 |
| `MANAGER` | 管理人员 | 跨模块经营管理和业务处置 | 全部非系统业务权限，不含合同删除 |
| `SALESPERSON` | 采销业务员 | 合同、执行批次和执行通知 | 合同创建/编辑/提交/作废、执行管理 |
| `LOGISTICS_OPERATOR` | 物流运营 | 运单、调度、在途和收货 | `logistics.manage` |
| `QUALITY_OPERATOR` | 地磅质检 | 磅单、质检单、复核和影像 | `quality.manage` |
| `WAREHOUSE_KEEPER` | 仓储库管 | 出入库、库存、台账和库存冲销 | `inventory.manage` |
| `FINANCE_SPECIALIST` | 财务结算 | 应收、应付和业务结算 | `settlement.manage` |
| `MASTER_DATA_ADMIN` | 主数据管理员 | 合作伙伴、服务生态、物料、仓库、车辆 | `master_data.manage` |
| `ORGANIZATION_ADMIN` | 组织管理员 | 企业、部门、员工和业务组 | `organization.manage` |
| `BUSINESS_MANAGER` | 业务主管 | 合同业务合理性审批 | `contract.approve` |
| `RISK_MANAGER` | 风控经理 | 合同风险与合规审批 | `contract.approve` |
| `GENERAL_MANAGER` | 总经理 | 合同最终经营决策审批 | `contract.approve` |
| `APPROVER` | 审批人 | 通用业务审核，当前用于库存冲销 | 合同审批及业务查看 |
| `USER` | 普通用户 | 基础业务协作 | 基础合同操作及各业务模块查看 |

岗位角色除本岗位管理权限外，只配置完成工作所必需的上游和下游查看权限。例如物流运营可以查看合同、执行批次、质检、库存和主数据，但不能修改这些模块；地磅质检可以查看运单但不能调度运单。

不为采购和销售分别创建权限相同的角色：当前权限粒度在合同模块层级，统一使用 `SALESPERSON`，通过数据范围区分本人、部门或企业数据。以后只有在采购与销售出现不同的服务端操作权限时，才新增对应权限编码和角色。

角色权限页同时支持逐项勾选和全局全选。全局全选基于权限字典接口返回的全部权限 ID 生成待保存集合；当全部权限已选中时再次点击会清空待保存集合。`ADMIN` 的全部权限由后端规则保证，前端固定显示为全选并禁止收窄。

### 配置与开发边界

| 事项 | 目标方式 | 当前实现 |
|------|----------|----------|
| 新增、编辑、停用角色 | 管理员页面配置 | API 已支持，前端入口待补 |
| 为角色组合已有权限 | 管理员页面配置 | 已支持逐项、全选、取消全选和保存 |
| 为用户授予角色及数据范围 | 管理员页面配置 | 已支持 |
| 新增权限编码 | 开发并发布 | 需增加权限字典、后端校验点、前端可见性控制和测试 |

权限编码不是普通业务字典。禁止只在数据库增加权限名称而不接入服务端鉴权，否则会形成“页面看似授权、接口实际不受控”的伪权限。

权限编码使用 `资源.操作`：

| 模块 | 查看 | 管理/专项操作 |
|------|------|---------------|
| 合同 | `contract.view` | `contract.create/edit/submit/approve/void/delete` |
| 执行 | `execution.view` | `execution.manage` |
| 物流 | `logistics.view` | `logistics.manage` |
| 磅单质检 | `quality.view` | `quality.manage` |
| 库存 | `inventory.view` | `inventory.manage` |
| 结算 | `settlement.view` | `settlement.manage` |
| 主数据 | `master_data.view` | `master_data.manage` |
| 组织系统 | `organization.view` | `organization.manage`、系统管理专项权限 |

外部企业范围是数据范围，不是角色模板。外部账号是否能创建或修改业务，仍取决于其角色是否包含管理权限。

## 外部企业账号

外部企业账号必须关联 `Company(type=EXTERNAL)`，该企业必须通过 `partnerId` 关联合作伙伴。

外部账号的数据范围固定为本企业全部关联数据，不能在授权页面切换为全平台或其他企业：

- 合同中本企业合作伙伴作为卖方；
- 合同中本企业合作伙伴作为买方；
- 合同中本企业合作伙伴作为签约主体；
- 合同下游执行批次、执行通知、物流、磅单、质检、库存和结算数据沿单据链继承。

这里的“全部”指企业级全部，不是平台级全部；同一外部企业的不同员工看到相同的企业关联数据，不限于本人创建。

外部企业未关联合作伙伴时拒绝访问业务数据，避免因为无法确认企业身份而意外放开权限。

## 范围构造与继承

`AccessControlService` 统一生成 Prisma `WhereInput`，业务 Service 将范围与自身状态、搜索条件组合：

| 目标模型 | 继承路径 |
|----------|----------|
| `Contract` | 卖方/买方/签约主体，或内部企业/部门/创建人范围 |
| `Order` | `contract` |
| `DispatchNotice` | `order.contract` |
| `Waybill` | `dispatchNotice.order.contract` |
| `WeighTicket` | `waybill.dispatchNotice.order.contract` |
| `QualityInspection` | `weighTicket.waybill...contract` |
| `InboundReceipt` | `waybill...contract` |
| `BusinessInbound` | `receipt.waybill...contract` |
| `InventoryLot` | `businessInbound.receipt...contract` |
| `InventoryLedger` | `lot.businessInbound.receipt...contract` |
| `OutboundReceipt` | `waybill...contract` |
| `SalesOutbound` | `receipt.waybill...contract` |
| `InventoryReversal` | 入库来源或出库来源范围的并集 |

附件查询必须在附件所属业务对象关系中附加同一范围，只有校验通过后才可生成对象存储临时查看地址。

## 管理约束

- Web 登录、令牌刷新、JWT 鉴权和小程序工作台统一校验账号、员工及企业均为有效状态。
- 停用账号或停用员工时清除刷新令牌；停用员工同步禁用关联账号，恢复员工后账号须由管理员单独启用。
- 员工跨企业调动时同步 `User.companyId`，并将非管理员角色范围收紧到新企业；部门必须属于员工所在企业。
- 关联账号后的姓名、手机号和邮箱以员工档案为准，账号用户名保持独立。
- 已关联账号的员工不得物理删除；只有无账号的误建档案可删除。
- 外部企业账号授权保存时强制改为 `COMPANY` 及本企业 ID。
- 外部企业不能授予 `ADMIN`。
- 一个外部企业最多 6 个有效账号。
- 系统至少保留一个有效系统管理员。
- 管理员可以处理全部当前合同审批节点；库存冲销审核支持有效 `ADMIN` 或 `APPROVER` 多角色。
- 合同只有作废后才能由管理员软删除。

- 角色、权限、用户授权和数据范围表；
- 14 个预置角色和 24 个基础权限；
- 现有用户角色数据迁移；
- 新建账号自动生成角色授权；
- 新账号默认所属企业范围，只有系统管理员默认全部数据；
- 员工与账号启停联动、企业状态统一登录校验、跨企业调动同步和账号操作审计；
- 外部企业最多 6 个有效账号；
- 外部企业角色范围强制锁定到所属企业；
- 合同列表、详情、附件、编辑、提交、审批、作废和删除接入统一鉴权；
- 执行批次和执行通知的列表、详情、创建、修改、状态流转接入统一鉴权；
- 物流运单的列表、详情、调度、状态流转和收货附件接入统一鉴权；
- 磅单和质检单的候选单据、列表、详情、业务操作和附件接入统一鉴权；
- 物流入库、销售出库、库存批次、库存台账和库存冲销接入统一鉴权；
- 库存冲销审核读取多角色授权，系统管理员和审批人均可处理；
- 合作伙伴、物料、仓库、车辆、服务生态接口接入 `master_data.view/manage`；
- 企业、部门、员工、业务组接口接入 `organization.view/manage`，用户账号接口接入 `system.user.manage`；
- 系统管理“用户与权限”页面。

单据范围继承链为：

`合同 → 执行批次 → 执行通知 → 物流运单 → 磅单 → 质检单 → 出入库 → 库存批次/库存台账/库存冲销`

后续新增结算单、发票、收付款等模块时，必须从合同或对应的出入库来源单继承同一企业范围，不允许仅按创建人过滤外部企业数据。

## 尚待接入

- 角色管理页面需补齐新增、编辑和停用入口，并复用现有 `POST/PATCH /access-control/roles` 接口。
- 合同审批人候选和节点处理需从旧 `User.role` 判断迁移为有效多角色及 `contract.approve` 权限判断。
- 主数据和组织数据尚未形成外部企业专属只读视图，现阶段只应向内部岗位授予对应查看或管理权限。
- 结算中心、发票、收付款尚无正式业务接口。
- 承运商、质检机构、仓储服务商作为非直接签约参与方的穿透访问需要新增参与方映射和字段级脱敏，不能直接复用合同签约方范围。
- 上述能力完成前，外部账号不得获得 `master_data.manage`、`organization.manage` 或任何系统管理权限。

## 业务单元、权限与审批收口

产品完整方案见[业务单元与权限审批优化方案](../../产品/业务单元与权限审批优化方案.md)。

### 目标数据模型

| 模型/字段 | 目标作用 |
|---|---|
| `Company.isManagementEntity` | 标识唯一的平台管理主体；承载部门、员工、账号和业务单元，不等同于合同签约主体 |
| `BusinessUnit` | 业务单元主数据，包含编码、名称、类型、平台管理主体、上级单元、利润中心编码和状态 |
| `UserBusinessUnit` | 用户与业务单元多对多归属，包含默认标识、状态和有效期 |
| `UserRoleScope(BUSINESS_UNIT)` | 指定某项角色授权适用的一个或多个业务单元 |
| `Contract.businessUnitId` | 合同唯一主业务单元，是审批、履约和经营统计的归属根 |
| `ApprovalFlowNode.scopeType=BUSINESS_UNIT` | 按合同业务单元及节点角色动态匹配审批人 |
| `InventoryLot.businessUnitId` | 库存经营归属；与 `ownerPartnerId`、仓库、物料和批次共同构成库存隔离口径 |

现有 `BusinessGroup` 与 `User.businessGroupId` 作为旧版兼容字段暂时保留，不再承担新权限判断；新能力使用 `BusinessUnit`、`UserBusinessUnit` 和 `UserRoleScope(BUSINESS_UNIT)`，禁止用逗号字符串保存多业务单元。

### 范围计算

内部用户的合同授权条件调整为：

```text
有效角色授权包含 permissionCode
  AND 该角色的 COMPANY / DEPARTMENT / BUSINESS_UNIT / SELF / ALL 范围覆盖合同
```

合同下游继续沿来源关系继承范围。业务入库、库存批次、库存台账、出库管理、销售出库和生产任务显式保存 `businessUnitId`，只能由服务端从来源单据或任务归属写入。库存冻结、生产领料和销售出库必须同时匹配业务单元与货权主体。

业务单元只归在唯一平台管理主体下；内部签约企业继续以合作伙伴 `Partner` 参与合同和库存。禁止通过签约主体反推业务单元，也禁止校验二者必须属于同一企业。

外部企业仍以合同卖方、买方或签约主体关系确定企业范围，不因内部业务单元规则缩小其应见的本企业关联数据；其功能权限仍采用外部业务白名单，且禁止访问全量主数据、组织和系统管理接口。

### 前端权限协议

- 侧栏按照 `*.view` 或专项查看权限显示普通业务模块；
- 操作按钮按照 `*.manage` 或具体动作权限显示；
- Web 与小程序共用权限语义，不以角色编码硬编码按钮；
- 应用外壳加载最新个人角色、权限、业务单元和默认业务单元；授权调整后主动刷新；
- 后端返回 403 时保留统一无权限提示，但不以 403 代替前端入口控制。

### 必测安全场景

- 同一用户在 A 单元有审批权限、B 单元只有查看权限；
- 同一用户多个角色的范围合并但不发生权限与范围交叉放大；
- 列表、详情、附件、导出、候选接口和首页统计的业务单元范围一致；
- 修改合同业务单元后必须重算审批路径，审批中和执行中禁止静默变更；
- 外部账号无法访问主数据、组织和系统管理接口，但可通过受限候选接口完成授权业务操作。

## 验证基线

- 外部企业合同范围匹配卖方、买方和签约主体三种参与方式。
- 外部企业未绑定合作伙伴时拒绝访问。
- 质检等深层单据生成的 Prisma 范围完整包含合同参与方条件。
- 业务模块单元测试注入范围服务，并验证自身业务状态和数量规则不受破坏。
- 当前回归基线：33 个 API 测试套件、228 项测试通过；前后端 TypeScript 检查和生产构建通过。
